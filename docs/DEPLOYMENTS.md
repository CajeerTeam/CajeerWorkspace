# Управляемое развёртывание 0.4.3

Workspace планирует и регистрирует деплой. Штатный поставляемый исполнитель `tools/deploy.py` выполняется локально на Linux-хосте, который обслуживает сайт aaPanel или CajeerServers. Это не вызов неподтверждённого API панели: обе интеграции 0.4.2 остаются read-only. Поддерживаются ZIP-артефакты веб-приложений без необратимых миграций и install hooks. Рабочие данные, конфигурация, секреты, uploads и БД находятся вне каталогов releases. Развёртывания БД и рестарт служб этим исполнителем не выполняются.

## Подготовка хоста

* Python 3.9+, Linux, PHP CLI с расширениями Workspace, `proc_open`. Используйте отдельного непривилегированного системного пользователя деплоя. Веб-пользователь целевого приложения не должен иметь права записи в root, releases, spool, journal. PHP-FPM и оператор Workspace также не должны разделять право записи в код или конфигурацию исполнителя. Для удалённого хоста потребуется штатный CLI Workspace с доступом к общей PostgreSQL БД; не размещайте SQLite на сетевой ФС. Ограничьте доступ к CLI и БД доверенными операторами. Не запускайте в качестве root.
* Создайте канонические каталоги `/srv/myapp` и `/srv/myapp-artifacts`, принадлежащие пользователю деплоя, без записи для группы и остальных. В aaPanel/веб-сервере document root должен указывать на `/srv/myapp/current/public` (если ZIP использует `public`) или другой подходящий подкаталог `current`. `current` должен быть символьной ссылкой; при необходимости настройте PHP realpath/opcache так, чтобы readiness отвечал от фактически исполняемого кода. Не публикуйте каталог releases, spool или journal отдельно.
* В проекте создайте окружение и привязку сайта; в матрице хоста задайте `site.deploy`, исполнителя aaPanel либо CajeerServers и пользователя с project `operations` (или владельца). Права проверяются при создании и повторно в транзакции перед запуском; не отзывайте или меняйте конфигурацию во время выполнения. Изменение матрицы site.deploy блокируется, пока выполняется деплой или требуется восстановление.
* Экспортируйте точную идентичность привязки операторской командой `php bin/workspace deploy:target SITE_ID`. Включите эту структуру **без изменений** в локальный конфиг `WORKSPACE_DEPLOY_CONFIG`, доступный только оператору (0600). Для каждого сайта отдельный root и отдельный единственный executor. Не используйте общий root между разными сайтами/окружениями.

Пример формирования конфигурации (site ID 12):

```sh
umask 077
export WORKSPACE_DEPLOY_CONFIG=/srv/secrets/workspace-deploy.json
target_file=$(mktemp)
php bin/workspace deploy:target 12 > "$target_file"
python3 - "$target_file" "$WORKSPACE_DEPLOY_CONFIG" <<'PY'
import json, sys
identity=json.load(open(sys.argv[1]))
with open(sys.argv[2], 'x') as out:
    json.dump({'targets': {str(identity['site_id']): {'identity':identity,
        'root':'/srv/myapp','spool':'/srv/myapp-artifacts',
        'health_url':'https://example.org/ready'}}},out,indent=2)
PY
rm "$target_file"
```

Probe фиксируется оператором, допускается HTTPS с проверкой сертификата либо HTTP только на loopback. Redirect запрещён. Endpoint должен отвечать HTTP 200, JSON `{"ready":true,"commit_sha":"<точный 40-символьный SHA исполняемой версии>"}` только после проверки реальных зависимостей. SHA должен соответствовать реально исполняемому коду, не возвращаться из запроса клиента или конфигурации Workspace. В CI включите build metadata в артефакт. Health не должен кэшироваться CDN. Для проверки используется до трёх попыток (5 с сетевого timeout, 1 с между попытками). Перед изменением проверяется и текущая версия.

## Начальная версия

Первичная миграция сайта требует ручного обслуживания и проверенного базового ZIP. Перенесите доверенный архив текущей версии из CI в spool под именем `<sha256>.zip`. Права только на чтение для исполнителя; не позволяйте приложению писать в spool. Укажите подтверждённый commit SHA, digest и размер, используя данные фактической сборки. Команда prepare проверяет SHA-256 байтов и безопасно распаковывает, но не меняет live pointer:

```sh
python3 tools/deploy.py prepare --config "$WORKSPACE_DEPLOY_CONFIG" < baseline.json
```

`baseline.json` содержит `target` (точный результат deploy:target), `commit` (40 hex), `digest` (64 hex), `size` (размер ZIP в байтах). После проверки и в окно обслуживания оператор создаёт ссылку `ln -s releases/<digest> /srv/myapp/current` (только если current отсутствует), настраивает document root и подтверждает готовность текущего сайта. Не заменяйте существующий каталог без резервной копии и предварительной репетиции. Храните прежний релиз и журнал вне резервных копий приложения отдельно.

## Планирование и исполнение

1. Подтвердите выпуск в Workspace 0.4.1: PR, tag, SHA, CI и артефакт. GitHub App должна оставаться активной. Получите точный ZIP из доверенной CI-сборки или GitHub Release; разместите файл `<sha256>.zip` в spool на целевом хосте. Код сравнивает и размер из доказательств выпуска, и фактический SHA-256. Передача файла оператором или CI, не загрузка через веб и не автоматическое скачивание GitHub.
2. В разделе проекта «Управляемое развёртывание» ответственный выбирает сайт, релиз и окно UTC (до 24 часов, до 30 дней вперед), подтверждает MFA. Повтор формы с тем же ключом не создаёт второго задания. Один незавершённый деплой на сайт.
3. На целевом хосте: `php bin/workspace deploy:pending SITE_ID`, затем `php bin/workspace deploy:work DEPLOYMENT_ID`. Для cron `php bin/workspace deploy:tick SITE_ID` каждую минуту под пользователем исполнителя, с правильным окружением. `tick` не запускает будущие задания; истёкшие окна завершаются отказом. Повторный запуск одного задания блокируется. Локальный конфиг проверяется до claim и при запуске executor. Снимок прав и привязки проверяется заново до запуска. После начала операция может закончиться и после окна (health/rollback); новая активация после окончания запрещена.
4. ZIP до 256 МиБ, распакованный объём до 1 ГиБ, 20 000 записей; только безопасные ASCII пути, без symlink, traversal, устройств, дубликатов, encrypted entries. ZIP копируется перед хешированием в частный staging-каталог. Содержимое не исполняется как shell. Файлы имеют 0644, каталоги 0755; архив должен быть готов к работе без executable hooks. Исполнитель хранит журнал с SHA и digest до и после, переключает `current` атомарным `rename` на одной ФС, затем проверяет readiness. Не используйте mutable application data внутри релиза. При отказе новая версия заменяется предыдущей и повторно проверяется её готовность.

## Восстановление

`rolled_back` означает, что предыдущий код восстановлен и probe успешен. `recovery_required` или оставшийся `running` означает неопределённый результат. Остановите исходный worker, не меняйте current вручную до выяснения состояния. На том же хосте с исходным конфигом выполните `php bin/workspace deploy:recover DEPLOYMENT_ID`. Незавершённый локальный журнал приводит к безопасному возврату предыдущего релиза, даже вне окна; уже завершённый журнал сверяется с фактическим current и readiness. Отсутствующий/повреждённый журнал или несогласованный current оставляет задание заблокированным: восстановите журнал/предыдущий release из резервной копии и повторите recovery. При отсутствии доказательств требуется ручное расследование, автоматический успех не выставляется. Не меняйте конфиг привязки и не удаляйте историю. Привязки с историей деплоев сохраняются, удаление запрещено.

Состояния: queued, running, succeeded, rolled_back, failed (не активировано), cancelled (до запуска), recovery_required. До/после SHA, актор, окно и итог отображаются в истории. Аудит фиксирует действия. Локальные журналы не содержат секретов; резервируйте их вместе с releases и конфигурацией. Очистка старых релизов вручную только после проверки отсутствия ссылок и незавершённых заданий. Rollback касается файлов приложения, не данных БД или внешних side effects: обеспечьте обратную совместимость и отдельную процедуру восстановления данных.
