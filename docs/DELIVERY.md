# Карточка поставки и QA · 1.4.0

Откройте проект → Выпуски проекта → выберите выпуск → Карточка поставки и QA. Ссылка также доступна из связанной задачи. Требуются права `work` и `connections` в конкретном проекте. Существующие роли owner, manager и developer имеют эти права при наличии доступа к проекту; отдельной роли QA не вводится. Создание/подтверждение выпуска остаётся за существующим ответственным с `manage` и `connections`. QA не заменяет подтверждение релиза, не запускает деплой и не изменяет задачу.

1. Подготовьте завершённую задачу с критериями приёмки и основным PR (обычная связь GitHub). В форме создания выпуска можно ввести до пяти дополнительных номеров PR на выбранную задачу через пробел или запятую. Лимит 20 задач и 30 связей на выпуск. Не повторяйте основной PR. Номера относятся только к активному репозиторию проекта.
2. Создайте карточку. Версия задачи, заголовок, критерии, основная связь и дополнительные PR фиксируются; изменения требуют новой карточки. Проверка GitHub читает каждый PR и проверяет факт merge, идентификатор репозитория и принадлежность merge commit к SHA тега. CI проверяется строго для этого SHA, а опубликованный asset — по имени, размеру и SHA-256. Ответственный подтверждает после повторной сверки. Поздние проверки другого SHA не учитываются.
3. Создайте развёртывание в зарегистрированном dev/staging/prod обычным маршрутом (см. [DEPLOYMENTS.md](DEPLOYMENTS.md)). Обновите доверенного исполнителя на целевом хосте до версии 1.4.0. Он сверяет ZIP и readiness, активный указатель и возвращает точный commit и digest. Привязка цели и хеш доказательств выпуска проверяются в карточке. Legacy-состояния без digest не принимаются автоматически.
4. В карточке видны критерии, PR, head/merge SHA, CI и время проверки, артефакт, окружения, последняя попытка и последний подтверждённый фактический SHA/digest (если последнее задание подтвердилось). Это наблюдение управляемого деплоя, не live-проверка хоста. Новая попытка (кроме отменённой до выполнения), изменение привязки, неуспешный деплой либо неизвестный исход делают предыдущий результат историческим. Внешние изменения вне управляемого деплоя автоматически не обнаруживаются.
5. QA проверяет критерии на конкретном сайте, выбирает «Принято» или «Не принято», записывает доказательства. POST защищён CSRF, требуется свежее MFA. Состояние задачи, репозитория, версии, релиза, деплоя и последнего решения повторно проверяется внутри транзакции. Повтор того же запроса не создаёт второе решение; устаревшая форма отклоняется. Результаты append-only, повторное испытание создаёт новую запись; новые деплои не наследуют решения. История последних 100 решений доступна на карточке. Отключение репозитория скрывает удалённые доказательства и историю QA.

## Обновление и приёмка

Миграция 039 добавляет `delivery_task_scope`, `delivery_reviews` и индекс составной идентичности деплоя. Предыдущие выпуски сохраняются без искусственного backfill критериев или QA. Для новых испытаний создайте новую карточку; прежние подтверждения не подменяются. Схема 39 поддерживается в SQLite и PostgreSQL.

```sh
python3 -B tests/delivery_schema.py
php tests/delivery_unit.php
php tests/delivery_db.php
php tests/project_release_unit.php
php tests/project_release_db.php
python3 -B tests/deploy_executor.py
```

Для PostgreSQL в отдельной тестовой БД используйте установленный регламент CI и `php tests/delivery_db.php --postgres`. На живом стенде проверяйте PR с разными merge SHA, повторную доставку, отдельные сайты и изоляцию двух организаций, отзыв роли, изменение задачи после приёмки, новый деплой и несовпадающий digest. Никакой production-допуск не создаётся этими командами без проверки стенда.
