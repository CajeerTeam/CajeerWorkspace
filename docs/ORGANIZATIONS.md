# Организации и PostgreSQL · 0.2.0

## Модель доступа

Выпуск 0.2.0 добавляет организации и команды. Миграция 004 создаёт организацию `Workspace` (ID 1), переносит все существующие учётные записи и их роли, присваивает старым проектам ID организации 1 и сохраняет прежний доступ всех участников к старым проектам. Задачи, кассовые операции, договоры, версии PDF, история соединений и ссылки остаются с прежними ID. Роль в `users` сохранена для совместимости старых данных; решения веб-приложения принимаются по `organization_members.role`.

Новые проекты видят владелец своей организации и явно добавленные участники. Менеджер проекта добавляет и исключает участников своей организации, назначает задачи только активным участникам проекта с рабочей ролью. Владелец может видеть все проекты **только выбранной организации**. Команды — отдельные группы внутри организации; само членство в команде не даёт права на проекты, финансы или PDF. Финансы доступны владельцу и бухгалтеру, документы — владельцу и юристу, и только по доступным проектам. Поиск, обзор, экспорт CSV, прямые ссылки и скачивание PDF используют эти же границы. Исключение из проекта снимает назначения пользователя (кроме владельца); исключение из организации также отзывает его сессии. Последнего активного владельца нельзя заблокировать через CLI.

Владелец открывает раздел «Команда», создаёт команду, приглашение или отдельную организацию; может переименовать организацию, переименовать или удалить команду. Переключатель организации находится в боковой панели; старые формы при переключении теряют CSRF-токен. Приглашение содержит email, роль и срок 1–168 часов; одноразовый случайный 256-битный код отображается один раз, в БД хранится только SHA-256. Передайте код приватным каналом лично указанному получателю. Автоматической почтовой доставки и независимой верификации email в 0.2.0 нет. Существующий пользователь должен войти под приглашённым email и принять код; новый регистрирует имя и пароль. Код не передаётся в URL. Приглашение не даёт доступа к отдельному проекту без последующего добавления. Роль `owner` при приглашении даёт полный административный доступ к этой организации; выдавайте её только доверенным совладельцам. Отозванный, использованный или истёкший код отклоняется. `user:add` остаётся операторской командой для первой организации; приглашения предназначены для остальных организаций.

Конфигурация интеграций и CLI принадлежат администратору установки, а не арендаторам. В одноорганизационном режиме старые ключи принадлежат организации 1. При создании второй организации каталог существующих ключей закрепляется за первой; все новые ключи необходимо назначить до опроса. Для новой организации создайте уникальный ключ в серверном JSON и назначьте:

```bash
php bin/workspace connection:assign customer2-book 2
php bin/workspace sync customer2-book
```

Не переиспользуйте ключи других организаций: история сохраняется под ключом, поэтому передача ранее использованных ключей запрещена. Владелец организации привязывает назначенное ей подключение к проекту. Остальные роли с правом чтения интеграций видят только подключения своих проектов. Полный CLI-профиль и протокол — привилегии оператора установки, не выдавайте shell пользователям арендаторов. При изменении конфигурации останавливайте web и sync, назначайте ключ до возобновления работы.

## Обновление SQLite 0.1.2 -> 0.2.0

Остановите web/FPM, cron, CLI и сохраните старый код, конфигурацию, секреты. Распакуйте обновление. Выполните `php bin/workspace doctor`, `php bin/workspace upgrade /absolute/pre-020.sqlite`, `php bin/workspace migrations`. Ожидаемая схема — 4. Снимок включает все PDF в BLOB, старые финансовые записи и пользователей. До запуска проверьте на копии права и количество проектов, суммы по валютам, скачивание редакций. Не меняйте SQL 001–003. Возврат — старый код и проверенная копия прежней схемы по [UPGRADE.md](UPGRADE.md); не открывайте схему 4 старым кодом.

## PostgreSQL 14+

Поддерживается отдельная выделенная БД с пустой схемой `public`, без других приложений. Используйте отдельную роль БД с правами на её схему и ограниченным сетевым доступом. PHP требует `pdo_pgsql` для PostgreSQL; для переноса дополнительно `pdo_sqlite`. Конфигурация через переменные окружения CLI/FPM:

```bash
export PGHOST=db.example.internal PGPORT=5432 PGDATABASE=workspace PGUSER=workspace
export PGSSLMODE=verify-full
# PGPASSWORD передайте через защищённый механизм секретов; не храните в репозитории.
# Для verify-full настройте доверенный CA libpq (PGSSLROOTCERT).
export WORKSPACE_DB=pgsql
php bin/workspace doctor
# Только если нужна пустая новая установка:
php bin/workspace init owner@example.org 'Владелец'
```

По умолчанию используется SQLite; для PostgreSQL явно `WORKSPACE_DB=pgsql`. `PGSSLMODE=disable` допустим только для изолированного локального теста. Для удалённого соединения используйте `verify-full`. `WORKSPACE_DATA` по-прежнему нужен для файлов сессий и блокировки опроса. Не размещайте его в docroot. Для нескольких PHP-хостов нужны общие сессии/операционные меры и единый экземпляр sync; распределённая эксплуатация не является целью 0.2.0. Записи PostgreSQL сериализуются транзакционной advisory-блокировкой приложения; это сохраняет инварианты предыдущего SQLite-движка, но ограничивает масштабирование.

### Перенос существующей установки

1. На копии обновите SQLite до 0.2.1 (схема 5). Остановите весь web, cron, worker и CLI на исходной базе и не возобновляйте запись до переключения. Убедитесь, что назначение — пустая PostgreSQL БД. Не выполняйте `init` в назначении.
2. Настройте PG-переменные, как выше, но оставьте `WORKSPACE_DB=sqlite`. Держите `WORKSPACE_DATA` на исходном каталоге. Подготовьте существующий защищённый каталог резервирования вне `public`.

```bash
export WORKSPACE_DB=sqlite
umask 077
php bin/workspace postgres:import /absolute/backup/pre-postgres.sqlite > /absolute/backup/import-report.json
```

3. Команда удерживает блокировку записи SQLite, создаёт согласованную копию и проверяет её целостность. В одной транзакции PostgreSQL создаются собственные миграции 001–004, переносятся все 18 таблиц бизнес-данных и системного состояния (включая приглашения, хеши паролей, протокол, денежные операции, BLOB -> BYTEA). Сохраняются ID, ссылки, даты и бинарные байты. Сверяются количество строк и SHA-256 нормализованных полных строк каждой таблицы, SHA-256 каждого PDF, внешние ключи и восстанавливаются значения последовательностей. Любое несовпадение отменяет целевую транзакцию. Журнал миграций назначения содержит собственные контрольные суммы SQL PostgreSQL; исходный журнал остаётся в SQLite-копии. Не повторяйте импорт в непустую базу. При ошибке копия остаётся доступной по указанному пути; проверьте состояние назначения, прежде чем повторять с новым путём.
4. Сохраните отчёт импорта и хеш снимка, переключите CLI/FPM на `WORKSPACE_DB=pgsql`. Используйте новый `WORKSPACE_DATA` для сессий (или удалите старые сессии при остановленном приложении), сохраните прежнюю защищённую конфигурацию интеграций (`WORKSPACE_CONFIG`), выполните `php bin/workspace migrations`, `/health.php`. Проверьте вход, права двух организаций, списки, поиск, CSV по валютам и две версии PDF. Проверьте новую операцию записи и следующее значение ID. Только после приёмки возобновите эксплуатацию. На старой SQLite не допускайте новых записей после переключения.
5. Если переключение не принято **до начала новых записей** в PostgreSQL, остановите приложение и верните SQLite-конфигурацию и неизменённый источник либо снимок, проверив SHA-256. После появления новых записей возврат к старому снимку потеряет эти записи; автоматической обратной синхронизации нет. Согласуйте окно и отдельную процедуру сверки.

Резервирование PostgreSQL: используйте штатный `pg_dump` из совместимого PostgreSQL-клиента, не SQLite-команду `backup`:

```bash
umask 077
pg_dump --format=custom --no-owner --no-acl --file=/absolute/backup/workspace.pg.dump
sha256sum /absolute/backup/workspace.pg.dump > /absolute/backup/workspace.pg.dump.sha256
pg_restore --list /absolute/backup/workspace.pg.dump
# Проверка восстановления в отдельной пустой базе:
pg_restore --exit-on-error --single-transaction --no-owner --no-acl --dbname=workspace_restore /absolute/backup/workspace.pg.dump
```

Используйте новые имена файлов и проверьте SHA-256 перед восстановлением. Секреты, конфигурация и код резервируются отдельно. В 0.2.1 поддерживается обновление PostgreSQL 4 → 5 после проверенного pg_dump; остальные неподдерживаемые исходные версии блокируются. См. [PERMISSIONS.md](PERMISSIONS.md).

## Приёмка

`python3 tests/tenant_schema.py` проверяет миграцию 004 и ограничения SQLite. `python3 tests/tenant_e2e.py` проверяет две организации на реальном PHP/SQLite. `python3 tests/tenant_e2e.py --postgres` дополнительно переносит заполненную SQLite в PostgreSQL, проверяет отказ при испорченном PDF, повторный импорт, чтение и запись в PostgreSQL и изоляцию. Для последнего теста нужны оба PDO-драйвера, cURL и выделенная пустая PostgreSQL БД. CI содержит отдельные задания с PostgreSQL. Проверки на живой инфраструктуре оператора обязательны перед production-переключением.
