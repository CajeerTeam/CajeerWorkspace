# CajeerEngine 2.1.0 · Workspace 0.7.0

## Setup
Use a dedicated Engine installation per project (root origin, HTTPS; loopback HTTP only for local tests). In Engine, create an API token with `content:read` and `content:write`; use a dedicated service credential, not a person's password. In Engine, run `php bin/console api-token:create --user-id=SERVICE_USER_UUID --name=workspace --scope=content:read --scope=content:write --expires="+30 days"` or use API tokens in the admin. The user must have the requested scopes. The token grants content access to the whole installation: do not share that installation across mutually untrusted projects. Do not provide write-enabled credentials to a read-only Workspace deployment. Set environment variables in PHP-FPM, not in public files. Example `config/connections.local.json`:

```json
{"engine-prod":{"type":"engine","base_url":"https://cms.example.com","installed_version":"2.1.0","secret_env":"WORKSPACE_ENGINE_PROD_TOKEN"}}
```

`installed_version` is an operator attestation, not a remote version probe. Upgrade/retest the integration before changing Engine version. Assign the connection to the correct organization using existing connection governance (single-organization initial installations may use unassigned keys). Owner opens Sites Engine, chooses project and binds the connection. Binding checks `/api/v1/content-types`; only one project may own the normalized origin or connection key. Do not configure alternate DNS aliases for the same installation. Disable a binding before retiring an installation. The binding is immutable; endpoint or secret-env changes require operator migration, not silent reassignment. Token rotation in the same environment variable is supported. Do not place private documents in an Engine accessible to this integration unless all users with project `connections` rights may read them.

## Workflow
* Users with project `connections` and fresh MFA can read the catalog, search, choose content type, and view the current or a retained historical revision. All fields are escaped text, not executable CMS HTML. This is an exact data preview, not a themed or asset-pinned visual rendering. History retention depends on Engine; large responses are rejected (4 MiB response; 512 KiB snapshot).
* Owner/manager with fresh MFA can prepare a publication for the current **draft** revision. The preview hash is checked against a fresh read, and a canonical snapshot is persisted. Historical/published/archived revisions cannot be published from this screen. One intent per site/type/id/revision; cancellation is final for that revision. A new revision is required for another attempt.
* Confirm the saved snapshot explicitly. Workspace records intent before remote I/O, checks the binding and current access again, reads the current entry, and compares the snapshot. `PATCH /api/v1/content/{type}/{id}` sends only `status=published` and integer `expected_revision`. Engine 2.1.0 serializes CMS writers and validates expected_revision inside its update path. The dedicated `/publish` endpoint does not accept a revision precondition and is intentionally not used. No restore, create, or unpublish is performed. Engine increments revision on success. Workspace compares returned ID and entire expected snapshot except server timestamps. An Engine schema change may cause normalization on update; unexpected content in the response is treated as uncertain, not confirmed.
* A confirmed response is recorded before read-only public route discovery. The list API's `public_path` is used only when the current entry exactly matches the expected published snapshot; up to 100 search candidates are examined. A non-routable type or large search result may have no link; recheck via the Engine UI. The link is the last observed route, not proof of current public accessibility. Reconcile updates it or clears it when the entry changes.
* In case of timeouts, process crash, or invalid response, do not repeat the write. An uncertain intent stays blocked for that revision; reconcile reads the entry and revision history. If the expected published snapshot is found, state becomes `observed` (not proof that this request was the publisher). A sending intent can be reconciled after 120 seconds. If evidence cannot be found, use Engine UI to investigate; never replay the uncertain request. No automatic retry of PATCH.
* The local operation holds the Workspace transaction lock during bounded GET/PATCH (up to 16 seconds). Use a request timeout above that limit and avoid bulk publishing. No remote transaction spanning the two services is claimed. Restoring an older Workspace backup does not undo Engine writes; reconcile before resuming.

## Verification
`php tests/engine_db.php` (SQLite, fixture transport); `python3 tests/engine_schema.py`; PostgreSQL transfer coverage `php tests/engine_db.php --postgres` on an empty target. Live acceptance requires Engine 2.1.0 configured with a disposable test draft: read catalog and revision, change draft after preview, verify conflict; publish fresh draft, check exact revision and public URL; repeat confirmation; disconnect token and verify no duplicate on recovery. No real site is modified by the fixture tests.
