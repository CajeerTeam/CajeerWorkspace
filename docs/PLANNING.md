# Планирование проектов · 0.3.0

## Рабочий процесс

1. Откройте проект. В разделе «Вехи проекта» менеджер проекта или владелец организации создаёт веху с названием и необязательным сроком. Прогресс рассчитывается по связанным задачам, а не вводится вручную.
2. Создайте задачи: название, обязательные заказчик результата (имя, команда или организация) и критерии приёмки (до 4000 символов, допускаются переносы строк), приоритет, необязательные исполнитель, срок и веха. Заказчик — текстовое бизнес-поле, не учётная запись и не выдача доступа. Исполнитель выбирается из участников с правом работы в проекте либо владельцев организации.
3. По ссылке на карточку задачи изменяйте план. Чтобы установить зависимость, укажите ID предшествующей задачи из того же проекта. В карточке видны оба направления связи, состояние и срок предшественника; ID отображается на доске и в backlog. Ссылку можно удалить. Зависимость означает «эта задача ждёт завершения предшественника».
4. Менеджер либо назначенный исполнитель переводит задачу из «К работе» в «В работе» или «Готово». Доска обновляется после отправки формы. Непосредственный переход к «Готово» разрешён, если все предшественники завершены и условия приёмки заполнены. Запись `done` фиксирует решение уполномоченного участника, а не электронную подпись клиента. Отдельное согласование заказчиком относится к будущим этапам.
5. Для закрытия вехи нужны минимум одна задача и все связанные задачи в `done` с заполненными условиями приёмки. Закрытая веха защищена от редактирования плана/статуса и добавления новых задач. Менеджер может повторно открыть веху. Если нужно вернуть завершённого предшественника в работу, сначала верните его активные или завершённые зависимые задачи в очередь (при необходимости откройте их вехи).

## Доска и backlog

- Доска показывает три существующих состояния `todo`, `doing`, `done`; backlog по умолчанию — все незавершённые задачи в одном упорядоченном списке. Явный фильтр состояния позволяет увидеть и завершённые задачи.
- Приоритеты: 1 критический, 2 высокий, 3 обычный, 4 низкий. Сортировка: приоритет, ближайший срок, ID. Без срока — после дат внутри своего приоритета.
- Фильтры комбинируются: текст, статус, приоритет, веха (включая отсутствие), исполнитель (включая неназначенного), блокировки, просроченные предшественники и собственная просрочка задачи. Сроки сравниваются с календарным днём UTC. Блокировки видны также в обзоре задач.
- Поиск по задачам выполняется по названию, заказчику и критериям; общий поиск включает вехи. Латинский ASCII и русский алфавит (включая Ё) нечувствительны к регистру на обоих backend. Символы `%`, `_`, `!` ищутся буквально. Остальные алфавиты зависят от сопоставления базы.
- Доска ограничена 50 задачами на колонку на страницу; в backlog — 50 на страницу. Ссылки переключают страницу всех колонок одновременно с сохранением фильтров. Для просмотра одной длинной колонки выберите статус. Общий поиск сохраняет прежний лимит 100 результатов на категорию.

## Инварианты и безопасность

Все HTTP-изменения проходят через существующие проверки CSRF, полномочий и ключей идемпотентности. Менеджеры/владельцы меняют планы, вехи и зависимости; исполнитель меняет только статус назначенной ему задачи. Чтение карточек, доски, поиска и зависимостей ограничено организацией и членством в проекте. Клиентский гостевой кабинет остаётся изолированным. Чувствительные операции из предыдущих версий сохраняют свои требования MFA.

Сервис повторно проверяет актуальные права внутри транзакции. SQLite сериализует запись `BEGIN IMMEDIATE`, PostgreSQL использует существующую транзакционную advisory-блокировку. Проверка цикла использует рекурсивный CTE; составные внешние ключи запрещают зависимости и вехи между проектами даже на уровне базы. Изменение задач, статусов и зависимостей проверяет версию задачи; изменение вехи — версию вехи. Все изменения попадают в действующий аудит проекта без сохранения текста критериев или заказчика. Редактирование уже заполненных условий завершённой задачи требует возвращения в очередь. Бизнес-инварианты обеспечиваются сервисом, прямое изменение таблиц в обход приложения не является поддерживаемым способом эксплуатации.

## Обновление

Миграции `database/007.sql` и `database/postgresql/007.sql` добавляют три поля в `tasks` и таблицы `milestones`, `task_milestones`, `task_dependencies`. Старые задачи не меняют статус, исполнителя, сроки, ID или версию. Обычный приоритет назначается по умолчанию; заказчик и условия остаются пустыми до заполнения менеджером. Незавершённые старые задачи без условий нельзя перевести в `done`. Уже завершённые задачи остаются завершёнными, но должны быть дополнены перед закрытием вехи. Исторические критерии не выдумываются.

Следуйте [UPGRADE.md](UPGRADE.md) для обновления 6 → 7. Для PostgreSQL предварительно сделайте и проверьте `pg_dump`. Импорт SQLite → PostgreSQL переносит новые поля, связи и вехи с проверкой числа строк и SHA-256, как и прочие данные; сохраняются бинарные PDF и их хеши. Схема назначения должна быть пустой. См. [ORGANIZATIONS.md](ORGANIZATIONS.md).

## Приёмка

```sh
php tests/planning_unit.php
python3 tests/planning_schema.py
php tests/planning_db.php
python3 tests/planning_e2e.py
# Только на пустой тестовой PostgreSQL БД с настроенными PG*:
php tests/planning_db.php --postgres
```

Проверки: изоляция проектов и организаций, назначение исполнителя, права, миграция с данными, идемпотентность, устаревшие формы, циклы, разблокирование, просроченный предшественник, закрытие/повторное открытие вехи, комбинированные фильтры, регистр и литеральные шаблоны поиска, перенос PDF и планирования. Полный запуск требует PDO SQLite, cURL и (для импорта) PDO PostgreSQL с PostgreSQL 14+.
