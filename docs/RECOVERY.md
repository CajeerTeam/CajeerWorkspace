# 0.9.1 — Scale & Recovery

Операционные инструменты для Linux/POSIX, Python 3.9+, PHP из требований Workspace. Схема 33 не меняется. Для PostgreSQL нужны `pg_dump`, `pg_restore`, `psql` и клиент той же основной версии, что и сервер. Пилот и production не должны одновременно писать в одну БД или объектное хранилище.

## 1. Нагрузочный профиль

Только согласованный стенд. Сначала разверните пилот по [PILOT.md](PILOT.md), создайте согласованный объём проектов, задач, счетов и файлов. Подготовьте отдельные сессии пользователей разных ролей. Сохраните заголовок Cookie каждой тестовой сессии в приватном файле 0600 вне приложения. Не используйте production-cookie. Для защищённых страниц требуется свежее MFA. Укажите маркер конкретного ожидаемого содержимого, а не общий заголовок страницы входа.

Пример `/secure/load.json`:

```json
{
  "origin": "https://staging.example.org",
  "requests": 600,
  "concurrency": 8,
  "timeout_seconds": 10,
  "p95_limit_ms": 800,
  "max_error_rate": 0.01,
  "routes": [
    {"name":"health","path":"/health.php","contains":"\"status\":\"ready\""},
    {"name":"project","path":"/?p=project&id=1","contains":"Pilot Internal","cookie_file":"/secure/pilot-owner.cookie"},
    {"name":"projects","path":"/?p=projects","contains":"Pilot OSS","cookie_file":"/secure/pilot-developer.cookie"}
  ]
}
```

```sh
python3 tools/load.py --staging --profile /secure/load.json
```

Фиксированный объём запросов, 1–100 параллельных потоков, GET только для разрешённых страниц, без перенаправлений, без записи тел, cookies и URL в отчёт. Измеряются p50/p95/p99 успешных запросов, throughput, ошибки, результаты по каждому маршруту. Неуспешный порог — код 1. Профиль читает реальные HTTP-страницы; он не измеряет нагрузку записи, фоновые HTTP-интеграции или многоплощадочную производительность. Порог и объём примера не являются согласованным SLA. Один cookie может сериализовать запросы PHP-сессией; используйте раздельные сессии. Повторите с несколькими объёмами, зафиксируйте серверные метрики, размеры таблиц, время теста и конфигурацию.

## 2. Согласованная копия

Остановите HTTP/FPM, cron, worker, внешние CLI и все другие процессы записи, дождитесь окончания запросов и обслуживания объектов. Флаг `WORKSPACE_RECOVERY_OFFLINE=1` — подтверждение оператора, не автоматическая блокировка сторонних процессов. Для PG настройте явные `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGSSLMODE`, безопасный источник пароля и `WORKSPACE_DB=pgsql`.

```sh
export WORKSPACE_RECOVERY_OFFLINE=1
python3 tools/recovery.py backup --backend sqlite \
  --data /srv/workspace-data --objects /srv/workspace-objects \
  --destination /secure/backups/2026-11-26
# PostgreSQL: --backend pgsql вместо sqlite, без --data.
```

Приватный каталог объектов должен существовать даже при отсутствии файлов. Каталог назначения должен быть новым, вне приложения, вне каталога источника. SQLite использует штатный API backup с учётом WAL, PG — custom-format `pg_dump` схемы public. Снимок проверяет журнал миграций, хеши строк всех таблиц, баланс кассы по организациям/валютам, дебет минус кредит по счетам/валютам, ключи и хеши активных PDF, квитанции подписания, FK (SQLite) и ключевые связи (PG), последовательности идентификаторов. До/после операции сравнивается источник. Копируются только реально используемые объекты, без мусора и удалённых PDF. Исторические хеши сохраняются. SQLite-копия дополнительно логически проверяется сразу; PostgreSQL — после реального restore. Неполный каталог не содержит корректного completion manifest. Код, настройки, внешние CMS, медиаданные других сервисов, права/роли кластера PostgreSQL и ключи сохраняются отдельной процедурой; PHP-сессии не копируются. Старые копии могут содержать удалённые позднее документы.

Копия содержит персональные и финансовые данные и хеши паролей. Хранить на зашифрованном носителе или в защищённом backup vault с отдельным контролем доступа. Инструмент сам не шифрует содержимое. Сохраните SHA-256 манифеста в отдельном доверенном хранилище. Самопроверка манифеста без доверенного внешнего хеша не доказывает подлинность. Передайте каталог и доверенный хеш на другую площадку, не меняя файлов и прав.

## 3. Восстановление и карантин

```sh
python3 tools/recovery.py verify --backup /secure/backups/2026-11-26 \
  --manifest-sha256 "$TRUSTED_MANIFEST_SHA256"
python3 tools/recovery.py restore --backup /secure/backups/2026-11-26 \
  --manifest-sha256 "$TRUSTED_MANIFEST_SHA256" \
  --destination /srv/workspace-recovered
```

Для PG предварительно создайте новую пустую БД на целевой площадке и смените PG-переменные на неё. Инструмент откажется от непустой public, не удаляет старую БД. Восстанавливает одной транзакцией, после чего сравнивает логический снимок. Если проверка после commit не прошла, цель остаётся в карантине; не запускайте её. Если восстановление прервалось, используйте новый каталог и новую пустую БД, а не очищайте автоматически данные. Точный контроль суммы и объекты проверяются до записи.

Всем PHP-FPM, CLI и worker новой площадки установите одинаковые `WORKSPACE_DATA=/srv/workspace-recovered/data` и `WORKSPACE_OBJECT_DIR=/srv/workspace-recovered/objects`. В PG это обязательно также для файла карантина. Не переносите старые PHP-сессии. До снятия карантина `database()` блокирует штатные веб-операции и worker. Не обходите защиту удалением файла. Проверьте отчёт RESTORE-REPORT.json, старый узел держите отключённым. **Восстановление очереди из старой копии не гарантирует отсутствие внешней отправки после точки копии.** Проверьте внешние квитанции и все записи, которые могли измениться после точки копии: Logs, Bots, подпись, CMS, Forum, деплой. Безопасно разрешите неопределённые операции согласно [RELIABILITY.md](RELIABILITY.md), [SIGNING.md](SIGNING.md), [LITE.md](LITE.md). Пока карантин действует, доступны только специальные recovery-команды; используйте чтение из внешних кабинетов и проверенный отчёт, не запускайте обычный CLI до ручного согласования. Не начинайте отправку пока не сопоставлены внешние побочные эффекты; при необходимости оставьте интеграции отключёнными в конфигурации и разберите очереди отдельно на изолированной копии. Решение о cutover принимает оператор.

```sh
export WORKSPACE_DATA=/srv/workspace-recovered/data
export WORKSPACE_OBJECT_DIR=/srv/workspace-recovered/objects
php bin/workspace recovery:mfa-check
php bin/workspace recovery:release-quarantine "$TRUSTED_MANIFEST_SHA256" --reviewed
```

Команда требует корректный отчёт, ключ и подтверждение оператора; не запускает worker. Отдельно включите HTTP, проверьте health, входы сотрудников, гостя, права, PDF и финансовые остатки; затем по одному включайте проверенные интеграции. Не включайте старую площадку. Не допускайте общих callback URL до переключения маршрутизации. Для PG пароль, TLS и роли целевого кластера настраиваются отдельно.

## 4. Репетиция отказов и метрики

`python3 tests/recovery.py` — реальная SQLite и файлы: два проекта в разных организациях, деньги в двух валютах, inline и объектный PDF, очередь; повреждение, запрет перезаписи, принудительное завершение процесса с незавершённой транзакцией и восстановление в другой каталог. `php tests/recovery_db.php` — реальный отдельный worker, убийство после commit захвата, сохранение lease, моделирование истечения lease без десятиминутного ожидания, stale claim, проверка ротации MFA и карантина. `python3 tests/recovery_http.py` — HTTP профиль на настоящем PHP-стенде. CI `recovery-postgres` — отдельный PostgreSQL 16, принудительный рестарт во время незавершённой транзакции, восстановление в другую БД с native pg_dump/restore. Не запускать destructive CI-тест на production.

На реальном стенде зафиксируйте согласованный объём, время отказа UTC, последнюю подтверждённую транзакцию, время последней проверенной копии, время восстановления и время успешного health/проверок ролей и возобновления нужных worker. При `restore --outage-at UNIX_SECONDS` отчёт даёт возраст копии на момент отказа (временная оценка RPO), время от отказа до проверенного офлайн-восстановления (часть RTO) и длительность процедуры. Для окончательного RTO прибавьте запуск и проверку сервиса. RPO в потерянных бизнес-операциях определяйте сравнением последней подтверждённой записи со снимком и внешними квитанциями; возраст копии не равен числу потерянных записей. Пороги утверждаются отдельно, инструмент не заявляет production SLA автоматически.

## 5. Ротация ключей

Создайте проверенную резервную копию и безопасно сохраните старый MFA master key для старых копий. Остановите все процессы. Подготовьте новый случайный 32-байтный hex-ключ в защищённом секрет-хранилище (не аргумент CLI, не лог, не репозиторий). Старый ключ остаётся в окружении команды до завершения транзакции.

```sh
export WORKSPACE_RECOVERY_OFFLINE=1
php bin/workspace recovery:mfa-check
php bin/workspace recovery:mfa-rotate < /secure/new-mfa-key.txt
# Теперь смените WORKSPACE_MFA_KEY во всех конфигурациях на новый.
php bin/workspace recovery:mfa-check
```

AES-GCM перешифровывает каждую существующую запись с тем же TOTP seed и last_step; при любой ошибке откатываются все изменения. Успех отзывает staff и OIDC-сессии. Это намеренно делает неактуальными подтверждения некоторых очередей, требующих session_version: повторно проверьте полномочия и подтвердите действия штатными средствами. После неопределённого завершения команды сначала проверьте новый и старый ключ через `recovery:mfa-check`, не повторяйте ротацию вслепую. Уничтожайте временный файл безопасно в рамках вашей политики. При восстановлении старой копии требуется её старый ключ. Для ротации API-ключей используйте штатный механизм каждого провайдера, меняйте secret только после остановки worker и сверки неизвестных операций. Регрессии `tests/logs_db.php`, `tests/reliability_db.php`, `tests/bots_db.php` проверяют защиту очередей при изменении credentials. Нельзя автоматически менять credential_hash у незавершённых запросов ради повтора. Ротация внешних секретов не выполняется универсальной командой.
