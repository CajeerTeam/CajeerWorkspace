# GitHub Releases — Workspace 1.2.1

Канал `stable` предназначен для обновления самого CajeerWorkspace, а не проектов из раздела «Выпуски проекта». Репозиторий фиксирован: `CajeerTeam/CajeerWorkspace`. В 1.2.1 реализованы публикация, проверка доступности/совместимости, скачивание и предварительный план. Установка обновления из сети, автоматический откат и планировщик не входят в этот выпуск.

## Издатель (доверенная отдельная машина)

1. Собрать полный ZIP на точном коммите, дождаться всех CI jobs. Провести приёмку и получить пять подписей согласно [PRODUCTION.md](PRODUCTION.md). `production.py publish` формирует закрытый комплект с отдельной подписью релизного ключа. Не использовать ключи из тестов. Исходный пакет 1.2.0 и его SHA-256 должны быть подтверждены при приёмке.
2. Создать неизменяемый lightweight-тег `v1.2.1`, указывающий на принятый коммит, и отправить его в GitHub. Защитить теги/релизы от изменения настройками репозитория. Подписанный annotated tag в формате 1 не поддерживается (подписываются метаданные и сам пакет). Публикация требует полного локального Git-репозитория с этим коммитом.
3. Передать через защищённое окружение `WORKSPACE_GITHUB_RELEASE_TOKEN`: токен GitHub App либо fine-grained PAT с Contents: write только на данном репозитории. Не передавать токен через аргументы или сохранять его в конфигурации PHP. Для изолированного издателя требуется Python 3.9+, Git, OpenSSL, HTTPS к api.github.com и uploads.github.com. Не запускать публикацию автоматически из PR/обычного CI.

```bash
python3 tools/github_release.py \
  --source /secure/checkout \
  --bundle /secure/releases/1.2.1 \
  --trust /secure/trust \
  --trust-sha256 TRUST_REGISTRY_SHA256 \
  --private-key /secure/release-private.pem
```

Инструмент повторно проверяет пять подписей, подпись релиза, свежесть закрытого допуска (7 суток), точные байты файлов относительно `ci_commit` и соответствие удалённого тега. Создаёт черновик; загружает четыре файла, сверяет размер и SHA-256 каждого asset из GitHub API, повторно проверяет тег, затем открывает релиз. Не перезаписывает существующие релизы. При сетевом сбое/ошибке останется черновик или (при потере ответа после открытия) уже опубликованный релиз: проверить его состояние вручную. Не удалять опубликованные релизы или менять тег для повторной попытки. Удалять только подтверждённый незавершённый черновик после проверки администратором и повторять публикацию с неизменным комплектом. Токен отозвать/убрать из среды после работы.

Публичные assets:

- `CajeerWorkspace-1.2.1.zip`: полный воспроизводимый пакет с внутренним SHA256SUMS.
- `CajeerWorkspace-1.2.1.zip.sig`: подпись пакета SHA-256 (RSA/EC).
- `workspace-release.json`: версия, тег, принятый SHA коммита, схема, разрешённые исходные версия/схема/хеш пакета, размер и SHA-256 пакета и подписи, минимальные PHP/SQLite/PostgreSQL/Python, архитектура, расширения, хеш матрицы, хеш закрытого допуска и отпечаток ключа.
- `workspace-release.json.sig`: подпись канонических точных байтов JSON (ключи отсортированы, без пробелов и перевода строки) тем же доверенным ключом. Хеш `acceptance.json` — публичное подтверждение связи с закрытым допуском, а не раскрытие отчётов. Пять подписей и персональные данные хранятся отдельно.

Проверка подписи метаданных вручную (ключ получить по независимому доверенному каналу, проверить его SHA-256):

```bash
openssl dgst -sha256 -verify /etc/workspace/release.pub.pem -signature workspace-release.json.sig workspace-release.json
openssl dgst -sha256 -verify /etc/workspace/release.pub.pem -signature CajeerWorkspace-1.2.1.zip.sig CajeerWorkspace-1.2.1.zip
sha256sum CajeerWorkspace-1.2.1.zip
```

Сравнить хеш и размер с подписанным JSON. Для штатного `release.py verify` нужен также файл `.sha256`; сформировать его из уже проверенного хеша и имени, не считать вычисленный самостоятельно хеш доказательством подписи.

## Установка и диагностика

В окружении FPM и CLI задать:

```ini
WORKSPACE_UPDATE_PUBLIC_KEY=/etc/workspace/release.pub.pem
WORKSPACE_UPDATE_KEY_SHA256=64_ШЕСТНАДЦАТЕРИЧНЫХ_СИМВОЛА
WORKSPACE_UPDATE_ADMIN_IDS=1
```

Указать фактический ID доверенного администратора установки (несколько ID через запятую без пробелов). Это дополнительное серверное полномочие; обычный владелец сторонней организации не получает доступ автоматически. Ключ и отпечаток должны совпадать с отдельно доставленным доверенным ключом release из реестра; публичный ключ доступен для чтения FPM, но не для записи. Не хранить приватный ключ или токен издателя на сервере Workspace. При ротации заменить ключ и pin только по проверенному внешнему каналу. Самоподписанный ключ из GitHub не принимается.

```bash
php bin/workspace updates:check
```

Веб-раздел «Обновления Workspace» доступен только указанному администратору с ролью owner и свежим TOTP. Веб не обращается к GitHub, не читает ZIP и не запускает процессы; он отображает последний отчёт CLI (до 24 часов, с проверкой версии, схемы и pin). Кнопка обновляет отображение, не инициирует скачивание. CLI выполняется доверенным оператором. Запросы публичные, без токена; приватные репозитории не поддерживаются. Для GitHub требуется HTTPS и разрешённые хосты `api.github.com`, `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`.

## Скачивание и предварительный план (1.2.1)

Создайте отдельный каталог за пределами дерева приложения и docroot. Доверенный оператор должен быть владельцем каталога; FPM имеет только права чтения отчёта через отдельную группу (пример для Linux; замените имена пользователей/группы на реальные):

```bash
sudo install -d -o workspace-operator -g workspace-report -m 2750 /var/lib/workspace-updates
```

Добавьте FPM в группу `workspace-report`, перезапустите FPM для применения групп. Не предоставляйте FPM права записи в этот каталог или к инструментам CLI. Установите `WORKSPACE_UPDATE_STATE_DIR=/var/lib/workspace-updates` в CLI и FPM, остальные настройки ключа — как выше. Родительские каталоги должны быть доверенными, без записи посторонними. В CLI нужны PHP с рабочим подключением к БД, Python 3.9+ и OpenSSL. Оператор должен иметь чтение установленного дерева и исходного полного ZIP, соответствующего подписанным метаданным (не ZIP патча и не GitHub source archive). Не запускайте от root. Для Python-дочернего процесса используйте доверенный PATH; не передавайте токены издателя.

```bash
php bin/workspace updates:check
php bin/workspace updates:download
php bin/workspace updates:plan /secure/previous/CajeerWorkspace-1.2.1.zip
```

Пример предполагает, что установлен 1.2.1 и опубликован более новый совместимый выпуск. Каждая команда заново проверяет текущий стабильный релиз и доверие. Скачивание допускается только при `compatible`; фиксированный репозиторий и разрешённые HTTPS redirects, без прокси и токена, ограничение 128 МиБ, дедлайн 180 секунд на asset (с сетевым тайм-аутом чтения 15 секунд). Поток записывается во временный приватный каталог, проверяются размер, SHA-256, подпись ZIP, внутренний SHA256SUMS, имена/типы/размеры записей, VERSION, схема, матрица и внутреннюю согласованность реестра миграций. Скачанный код не извлекается и не исполняется. После проверки каталог атомарно переименовывается в `packages/<sha256>` (0700). Повторная команда переиспользует только заново проверенный пакет; повреждённый каталог блокирует операцию, его можно переместить в карантин вручную после остановки CLI. Частичный сетевой сбой не оставляет опубликованного пакета; повтор скачивает заново. При аварийном завершении процесса возможны приватные `.stage-*` каталоги, удаляемые оператором только при отсутствии выполняющейся операции. Учитывайте свободное место и периодически удаляйте старые неиспользуемые пакеты вручную. Блокировка предотвращает параллельные команды.

`updates:plan` повторно проверяет пакет, сравнивает точный SHA-256 исходного ZIP из подписанного списка `supported_from` с переданным файлом, сверяет все файлы исходного дистрибутива с установленным деревом и неизменность прошлых миграций, проверяет Python, выводит количество добавленных/изменённых/удалённых файлов, исходную и целевую схемы, список новых миграций и обязательные шаги обслуживания. Дополнительные локальные файлы не удаляются и не считаются частью исходного дистрибутива. План не меняет БД или рабочий код; не проверяет работоспособность будущего FPM или резервной копии и не является разрешением на установку. Согласованная копия, проверка восстановления, остановка писателей, повторная верификация и production-допуск обязательны. Существующий офлайн-регламент [PRODUCTION.md](PRODUCTION.md) остаётся действующим; автоматической установки нет.

`compatible` — версия и схема входят в разрешённый переход, текущие CLI PHP и БД удовлетворяют требованиям; проверены подпись метаданных, тег и объявленные GitHub digests. `incompatible` — причины перечислены. `current`/`ahead` — нет более нового релиза. `empty` — нет стабильных релизов. `downloaded` — байты пакета и подпись подтверждены. `planned` — предварительный план сформирован. `failed` — ошибка конфигурации, транспорта, подписи, исходного дерева или иной проверки; exit 1. При повреждении новейшего релиза нет тихого перехода к более старому. Проверяется до 300 записей с общим сетевым дедлайном 22 секунды для discovery. Проверка не гарантирует, что GitHub показал все существующие релизы. Полный пакет 1.2.1 поддерживает production-переход только с 1.2.0; схема остаётся 36. Переход и возврат выполняются по PRODUCTION.md.
