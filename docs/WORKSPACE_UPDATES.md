# GitHub Releases — Workspace 1.5.2

Канал `stable` предназначен для обновления самого CajeerWorkspace, а не проектов из раздела «Выпуски проекта». Репозиторий фиксирован: `CajeerTeam/CajeerWorkspace`. В 1.2.3 доступны stable/preview, ручная установка и добровольный автоматический запуск с пилотным допуском. По умолчанию автоматика выключена.

## Издатель (доверенная отдельная машина)

1. Собрать полный ZIP на точном коммите, дождаться всех CI jobs. Провести приёмку и получить пять подписей согласно [PRODUCTION.md](PRODUCTION.md). `production.py publish` формирует закрытый комплект с отдельной подписью релизного ключа. Не использовать ключи из тестов. Исходный пакет 1.2.3 и его SHA-256 должны быть подтверждены при приёмке.
2. Создать неизменяемый lightweight-тег `v1.5.2`, указывающий на принятый коммит, и отправить его в GitHub. Защитить теги/релизы от изменения настройками репозитория. Подписанный annotated tag в формате 1 не поддерживается (подписываются метаданные и сам пакет). Публикация требует полного локального Git-репозитория с этим коммитом.
3. Передать через защищённое окружение `WORKSPACE_GITHUB_RELEASE_TOKEN`: токен GitHub App либо fine-grained PAT с Contents: write только на данном репозитории. Не передавать токен через аргументы или сохранять его в конфигурации PHP. Для изолированного издателя требуется Python 3.9+, Git, OpenSSL, HTTPS к api.github.com и uploads.github.com. Не запускать публикацию автоматически из PR/обычного CI.

```bash
python3 tools/github_release.py \
  --source /secure/checkout \
  --bundle /secure/releases/1.5.2 \
  --trust /secure/trust \
  --trust-sha256 TRUST_REGISTRY_SHA256 \
  --private-key /secure/release-private.pem
```

Инструмент повторно проверяет пять подписей, подпись релиза, свежесть закрытого допуска (7 суток), точные байты файлов относительно `ci_commit` и соответствие удалённого тега. Создаёт черновик; загружает четыре файла, сверяет размер и SHA-256 каждого asset из GitHub API, повторно проверяет тег, затем открывает релиз. Не перезаписывает существующие релизы. При сетевом сбое/ошибке останется черновик или (при потере ответа после открытия) уже опубликованный релиз: проверить его состояние вручную. Не удалять опубликованные релизы или менять тег для повторной попытки. Удалять только подтверждённый незавершённый черновик после проверки администратором и повторять публикацию с неизменным комплектом. Токен отозвать/убрать из среды после работы.

Публичные assets:

- `CajeerWorkspace-1.5.2.zip`: полный воспроизводимый пакет с внутренним SHA256SUMS.
- `CajeerWorkspace-1.5.2.zip.sig`: подпись пакета SHA-256 (RSA/EC).
- `workspace-release.json`: версия, тег, принятый SHA коммита, схема, разрешённые исходные версия/схема/хеш пакета, размер и SHA-256 пакета и подписи, минимальные PHP/SQLite/PostgreSQL/Python, архитектура, расширения, хеш матрицы, хеш закрытого допуска и отпечаток ключа.
- `workspace-release.json.sig`: подпись канонических точных байтов JSON (ключи отсортированы, без пробелов и перевода строки) тем же доверенным ключом. Хеш `acceptance.json` — публичное подтверждение связи с закрытым допуском, а не раскрытие отчётов. Пять подписей и персональные данные хранятся отдельно.

Проверка подписи метаданных вручную (ключ получить по независимому доверенному каналу, проверить его SHA-256):

```bash
openssl dgst -sha256 -verify /etc/workspace/release.pub.pem -signature workspace-release.json.sig workspace-release.json
openssl dgst -sha256 -verify /etc/workspace/release.pub.pem -signature CajeerWorkspace-1.5.2.zip.sig CajeerWorkspace-1.5.2.zip
sha256sum CajeerWorkspace-1.5.2.zip
```

Сравнить хеш и размер с подписанным JSON. Для штатного `release.py verify` нужен также файл `.sha256`; сформировать его из уже проверенного хеша и имени, не считать вычисленный самостоятельно хеш доказательством подписи.

## Установка и диагностика

В окружении FPM и CLI задать:

```ini
WORKSPACE_UPDATE_PUBLIC_KEY=/etc/workspace/release.pub.pem
WORKSPACE_UPDATE_KEY_SHA256=64_ШЕСТНАДЦАТЕРИЧНЫХ_СИМВОЛА
WORKSPACE_UPDATE_ADMIN_IDS=1
```

Указать фактический ID доверенного администратора установки (несколько ID через запятую без пробелов). Это дополнительное серверное полномочие; обычный владелец сторонней организации не получает доступ автоматически. Ключ и отпечаток должны совпадать с отдельно доставленным доверенным ключом release из реестра; публичный ключ доступен для чтения FPM, но не для записи. Не хранить приватный ключ или токен издателя на сервере Workspace. При ротации заменить ключ и pin только по проверенному внешнему каналу. Самоподписанный ключ из GitHub не принимается.

```bash
php bin/workspace updates:check
```

Веб-раздел «Обновления Workspace» доступен только указанному администратору с ролью owner и свежим TOTP. Веб не обращается к GitHub, не читает ZIP и не запускает процессы; он отображает последний отчёт CLI (до 24 часов, с проверкой версии, схемы и pin). Кнопка обновляет отображение, не инициирует скачивание. CLI выполняется доверенным оператором. Запросы публичные, без токена; приватные репозитории не поддерживаются. Для GitHub требуется HTTPS и разрешённые хосты `api.github.com`, `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`.

## Скачивание и предварительный план

Создайте отдельный каталог за пределами дерева приложения и docroot. Доверенный оператор должен быть владельцем каталога; FPM имеет только права чтения отчёта через отдельную группу (пример для Linux; замените имена пользователей/группы на реальные):

```bash
sudo install -d -o workspace-operator -g workspace-report -m 2750 /var/lib/workspace-updates
```

Добавьте FPM в группу `workspace-report`, перезапустите FPM для применения групп. Не предоставляйте FPM права записи в этот каталог или к инструментам CLI. Установите `WORKSPACE_UPDATE_STATE_DIR=/var/lib/workspace-updates` в CLI и FPM, остальные настройки ключа — как выше. Родительские каталоги должны быть доверенными, без записи посторонними. В CLI нужны PHP с рабочим подключением к БД, Python 3.9+ и OpenSSL. Оператор должен иметь чтение установленного дерева и исходного полного ZIP, соответствующего подписанным метаданным (не ZIP патча и не GitHub source archive). Не запускайте от root. Для Python-дочернего процесса используйте доверенный PATH; не передавайте токены издателя.

```bash
php bin/workspace updates:check
php bin/workspace updates:download
php bin/workspace updates:plan /secure/previous/CajeerWorkspace-1.5.2.zip
```

Пример предполагает, что установлен 1.5.2 и опубликован более новый совместимый выпуск. Каждая команда заново проверяет выбранный канал и доверие. Скачивание допускается только при `compatible`; фиксированный репозиторий и разрешённые HTTPS redirects, без прокси и токена, ограничение 128 МиБ, дедлайн 180 секунд на asset (с сетевым тайм-аутом чтения 15 секунд). Поток записывается во временный приватный каталог, проверяются размер, SHA-256, подпись ZIP, внутренний SHA256SUMS, имена/типы/размеры записей, VERSION, схема, матрица и внутреннюю согласованность реестра миграций. Скачанный код не извлекается и не исполняется. После проверки каталог атомарно переименовывается в `packages/<sha256>` (0700). Повторная команда переиспользует только заново проверенный пакет; повреждённый каталог блокирует операцию, его можно переместить в карантин вручную после остановки CLI. Частичный сетевой сбой не оставляет опубликованного пакета; повтор скачивает заново. При аварийном завершении процесса возможны приватные `.stage-*` каталоги, удаляемые оператором только при отсутствии выполняющейся операции. Учитывайте свободное место и периодически удаляйте старые неиспользуемые пакеты вручную. Блокировка предотвращает параллельные команды.

`updates:plan` повторно проверяет пакет, сравнивает точный SHA-256 исходного ZIP из подписанного списка `supported_from` с переданным файлом, сверяет все файлы исходного дистрибутива с установленным деревом и неизменность прошлых миграций, проверяет Python, выводит количество добавленных/изменённых/удалённых файлов, исходную и целевую схемы, список новых миграций и обязательные шаги обслуживания. Дополнительные локальные файлы не удаляются и не считаются частью исходного дистрибутива при планировании; ручной установщик требует точное дерево и откажется от переключения, пока такие файлы не вынесены из релиза. План не меняет БД или рабочий код; не проверяет работоспособность будущего FPM или резервной копии и не является разрешением на установку. Согласованная копия, проверка восстановления, остановка писателей, повторная верификация и production-допуск обязательны. Существующий офлайн-регламент [PRODUCTION.md](PRODUCTION.md) остаётся действующим; автоматическая установка использует тот же проверяемый процесс.

`compatible` — версия и схема входят в разрешённый переход, текущие CLI PHP и БД удовлетворяют требованиям; проверены подпись метаданных, тег и объявленные GitHub digests. `incompatible` — причины перечислены. `current`/`ahead` — нет более нового релиза. `empty` — нет релизов выбранного канала. `downloaded` — байты пакета и подпись подтверждены. `planned` — предварительный план сформирован. `failed` — ошибка конфигурации, транспорта, подписи, исходного дерева или иной проверки; exit 1. При повреждении новейшего релиза нет тихого перехода к более старому. Проверяется до 300 записей с общим сетевым дедлайном 22 секунды для discovery. Проверка не гарантирует, что GitHub показал все существующие релизы. Полный пакет 1.5.2 поддерживает production-переход только с 1.5.1; схема обновляется 44 → 45. Переход и возврат выполняются по PRODUCTION.md.

## Ручная установка подписанного выпуска

Установка выполняется на Linux/POSIX из **уже скачанного пакета**, без сетевых обращений. Не выполняйте её из FPM, от имени веб-пользователя с публичным доступом к CLI или с доверенным ключом, полученным из самого ZIP. План должен быть успешным и не старше 24 часов; `updates:check` или `updates:download` после плана заменяют отчёт, поэтому план сформируйте последним. Заново проверяются подпись метаданных по pin, подписанный список допустимых переходов, версия/схема и SHA-256 исходного ZIP, целевой ZIP и его подпись, матрица, сохранность миграций, точное дерево установленного дистрибутива и PHP/БД среда. Включая исходный `SHA256SUMS`. Не требуется жёстко заданная пара версий в установщике.

### Подготовка площадки

- Управляемое дерево: `/srv/workspace-release-set/releases/<версия>` с полным проверенным дистрибутивом и `/srv/workspace-release-set/current` — относительная символическая ссылка `releases/<версия>`. Docroot: `current/public`, CLI/worker: `current/bin/workspace`. Для первичной подготовки используйте принятый офлайн-регламент [PRODUCTION.md](PRODUCTION.md). Не указывайте Git checkout или папку с локальными изменениями. Не размещайте `.env`, конфиги, данные и ключи в каталоге релиза; вынесите локальные файлы и Python `__pycache__` после проверки. Дальнейшие команды Python выполняйте с `-B`.
- `WORKSPACE_DATA`, `WORKSPACE_OBJECT_DIR`, `WORKSPACE_UPDATE_STATE_DIR` и managed root — четыре отдельные канонические абсолютные директории (не вложенные друг в друга). Данные и объекты 0700, state/managed root/release dirs без групповой записи и доступа остальных. Обеспечьте доверенного оператора с доступом к приватным данным и правом переключать код; все процессы Workspace должны иметь доступ к одному каталогу данных/блокировке. Для FPM — чтение дерева и отчёта, но не запись в каталог обновлений. В отдельной группе выставите setgid на родительских каталогах релизов/отчётов. Протестируйте права на тестовом стенде; не запускайте миграции от root, если рабочий пользователь не сможет читать/писать созданные файлы. Сохраните конфигурацию и ключи отдельно; оставьте достаточно места для полного ZIP, нового дерева, резервной копии и тестового восстановления.
- Перед установкой остановите входящий трафик, cron, timers, очереди, сторонние процессы и все другие узлы с доступом на запись. `--stop-unit` можно повторить для реальных systemd service/timer/socket/path: установщик выполняет `systemctl stop` и проверяет `LoadState` и `ActiveState` каждой единицы. Настройте точные права systemd/Polkit либо остановите службы доверенным администратором самостоятельно (например, aaPanel). `--offline-confirmed` обязателен: это подтверждение остановки **всех** других писателей и исключения их автоматического старта, не имитация остановки. Прямые SQL/файловые писатели и старый код до 1.2.2 не участвуют во flock; их необходимо остановить извне.
- Код 1.2.2+ удерживает общую блокировку `WORKSPACE_DATA/update-access.lock` на всё время запроса/CLI с БД. Установщик захватывает исключительную блокировку (если запрос ещё работает — завершится с ошибкой, повторить после остановки), сохраняет `update-maintenance.json` и удерживает общую блокировку операций обновления. Обычные HTTP/CLI получают 503 при обслуживании. Исключение — только дочерние CLI установщика с токеном операции; не задавайте этот токен в FPM/cron. Маркер сохраняется после аварийного завершения. Не удаляйте файл блокировки или маркер вручную.

```bash
# С доверенной установленной версии 1.2.2+ при наличии более нового подписанного релиза:
php /srv/workspace-release-set/current/bin/workspace updates:check
php /srv/workspace-release-set/current/bin/workspace updates:download
php /srv/workspace-release-set/current/bin/workspace updates:plan /secure/previous/CajeerWorkspace-1.5.2.zip

# После остановки всех внешних писателей; заменить пути и имена юнитов на реальные.
ARGS=(--root /srv/workspace-release-set --previous /secure/previous/CajeerWorkspace-1.5.2.zip \
      --data "$WORKSPACE_DATA" --objects "$WORKSPACE_OBJECT_DIR" --offline-confirmed \
      --stop-unit workspace-worker.service --stop-unit php8.4-fpm.service)
php /srv/workspace-release-set/current/bin/workspace updates:install "${ARGS[@]}"
php /srv/workspace-release-set/current/bin/workspace updates:status
# После проверки результатов и готовности к возобновлению трафика:
php /srv/workspace-release-set/current/bin/workspace updates:finish "${ARGS[@]}"
```

Для PostgreSQL задайте явные `WORKSPACE_DB=pgsql`, `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGSSLMODE` и безопасный способ передачи пароля libpq/PDO. Обязателен дополнительный параметр `--pg-restore-database workspace_restore_test` — **заранее созданная пустая БД на том же сервере**, отличная от рабочей, недоступная внешним писателям. Установщик делает `pg_dump`, проверяет хеши, восстанавливает в тестовую БД и сравнивает логический снимок, прежде чем запускать миграции. Не очищает и не перезаписывает непустую тестовую БД. Если восстановление прервалось, отдельно разберите и подготовьте тот же пустой тестовый контур. После приёмки удалите тестовую БД по своему регламенту хранения. SQLite проверяет копию через backup API, integrity/foreign-key check, хеши таблиц и файлов. Копируются все объекты, на которые ссылаются рабочие документы и архивы подписания; бесхозные файлы не считаются частью логического снимка.

### Журнал, сбой и возврат

`updates:install` записывает фазы `quiescing → guarded → backup_started → backed_up → staged → migrating → migrated → switched`. Длительно хранящиеся закрытые журналы и копии находятся в `WORKSPACE_UPDATE_STATE_DIR/packages/transactions/<id>/`, указатель последней операции — `packages/install.json`. Запись JSON и переключение `current` выполняются атомарной заменой с fsync. Приватный журнал содержит токен обслуживания и пути, не публикуется в вебе. В FPM выводится только обезличенный отчёт; во время обслуживания доступ к вебу закрыт. После сбоя `updates:status` показывает последнюю завершённую фазу и хеш резервной копии. Повторите `updates:install` **с теми же параметрами**: частичная копия изолируется, проверенная копия переиспользуется; допустимо продолжение с точного исходного снимка или проверенного целевого состояния. При расхождении остановиться и восстановить данные. Старая схема не заменяется простым переключением кода. При неизменной схеме проверяется весь логический снимок; при повышении — реестр миграций, отсутствие потери таблиц/строк, денежные контрольные суммы и объекты. Релиз с намеренной трансформацией/удалением этих данных требует отдельной приёмки, а не обхода проверки.

`switched` означает, что код переключён и CLI doctor/версия/схема/активный владелец, снимок и объекты подтверждены, **не** что FPM и внешние сервисы готовы. До `finish` запись закрыта. `finish` повторно проверяет целевое дерево, CLI и снимок, снимает маркер; системные службы остаются остановленными. Оператор запускает их, проверяет `/health.php`, живой вход, worker и сверку внешних операций перед открытием входящего трафика; при ошибке снова остановить писателей. FPM и полный рабочий цикл проверяются также на изолированной копии до production-перехода. Никаких внешних действий установщик не воспроизводит. Не включайте автозапуск узлов до явного завершения.

До `finish` команда `updates:rollback` с теми же параметрами возвращает `current` только после проверки полного исходного снимка и CLI. При несовпадении (включая повышенную схему) сначала выполнить контролируемое восстановление из проверенной копии на изолированном контуре по RECOVERY.md, сверить внешние операции, затем вернуть исходные данные в согласованную площадку. При невозможности восстановить исходное состояние маркер остаётся, автоматического отката нет. После `finish` откат по старой копии не разрешён: возможны новые платежи, подписи и публикации, нужен отдельный reviewed recovery. Если установка не дошла до проверенной копии, можно повторить её либо отменить через `updates:rollback`: команда проверит точное исходное дерево, схему, целостность и доступность исходного состояния. Возврат не требует чтения повреждённого целевого ZIP. Не снимайте защиту вручную.

**Переход 1.5.1 → 1.5.2:** установите подписанный stable-выпуск штатным установщиком 1.5.1 или офлайн по PRODUCTION.md. Сохраните полный подписанный ZIP 1.5.1. ZIP изменённых файлов предназначен для обновления исходного репозитория, а не для прямого production-развёртывания. AI выключен по умолчанию; отдельно настройте [пилот](AI_ASSISTANT.md).

## Автоматические обновления (1.2.3)

Издатель использует `tools/github_release.py --channel stable` (по умолчанию) или `--channel preview`. Preview публикуется как GitHub prerelease, не latest. Подписанный `channel` должен совпадать с признаком prerelease. Оба канала требуют обычного допуска и пяти подписей; один неизменяемый тег — один выпуск, не повышайте preview до stable путём редактирования тега или метаданных. Stable исключает preview; preview выбирает самый новый выпуск обоих каналов. Поддерживаются обычные числовые версии `X.Y.Z`; предварительный выпуск обозначается каналом, а не суффиксом версии. Ручной CLI выбирает stable по умолчанию; для preview задайте `WORKSPACE_UPDATE_CHANNEL=preview` в окружении конкретной команды. FPM не скачивает и не устанавливает пакеты.

### Настройка установки

Автоматический запуск выполняет отдельный непривилегированный оператор на Linux с Python 3.9+, системной базой часовых поясов (tzdata), PHP CLI, OpenSSL, управляемым деревом `current`, рабочими DB/объектами и уже настроенным доверенным release key. Используйте отдельного пилота и один общий, доступный по доверенному пути каталог подтверждений, который может изменять только пилотный оператор; остальным — read-only. Каталог и файл публичного pilot key не должны быть доступны на запись FPM. Ключ пилота отдельный от ключа выпуска; передайте его SHA-256 по независимому каналу. Приватный ключ пилота хранится отдельно и используется только при явном утверждении, не в timer и не на follower.

Пример файла `/etc/workspace/update-schedule.json` (замените пути, SHA-256, реальные юниты):

```json
{
  "root": "/srv/workspace-release-set",
  "archive_dir": "/secure/previous",
  "channel": "stable",
  "role": "pilot",
  "timezone": "Europe/Warsaw",
  "days": [6, 7],
  "start": "23:00",
  "end": "03:00",
  "hooks": {
    "quiesce": "/etc/workspace/hooks/quiesce",
    "start": "/etc/workspace/hooks/start",
    "health": "/etc/workspace/hooks/health",
    "open": "/etc/workspace/hooks/open",
    "notify": "/etc/workspace/hooks/notify"
  },
  "approval_dir": "/srv/workspace-rollout",
  "approval_key": "/etc/workspace/pilot.pub.pem",
  "approval_pin": "REPLACE_WITH_SHA256",
  "stop_units": ["workspace-worker.service", "php8.4-fpm.service"],
  "pg_restore_database": null
}
```

Для follower используйте `role=follower` и тот же pin/каталог допусков. Для PostgreSQL требуется заранее подготовленная **пустая** restore-test БД, отличная от рабочей; настройте `pg_restore_database` и подготовьте её перед каждым обновлением по разделу ручной установки. Точный исходный полный ZIP должен находиться в `archive_dir` или в проверенном хранилище скачанных пакетов; сохраняйте его до следующего выпуска. Файлы конфигурации, ключи и hooks — канонические абсолютные пути, владелец root или оператор, без записи другими пользователями. Не предоставляйте оператору произвольный sudo. Ограничьте полномочия системных hooks и проверьте всё на отдельном стенде.

Обязательные исполняемые hooks — реальные операции вашей площадки, а не команды-заглушки: `quiesce` идемпотентно закрывает ingress, отключает автозапуск, останавливает все внешние писатели и подтверждает это кодом 0; `start` запускает FPM/worker только при закрытом ingress; `health` проверяет фактическую готовность FPM, вход, worker и сверку (без повторной отправки платежей/подписей); `open` открывает ingress после успешных проверок. Каждый получает JSON с идентичностью релиза на stdin, тайм-аут 120 секунд, ненулевой exit означает отказ. Hooks должны быть идемпотентны и проверять фактическое состояние. `notify` необязателен: получает только UTC-время, статус и версию на stdin в очищенном окружении, может доставлять уведомление через ваш локальный агент. Его отказ отмечается в UI и не отменяет безопасное завершение установки. Без hook уведомления остаются в journal и интерфейсе (последние 20, закрытая история 100). Не передавайте секреты в вывод.

```bash
php /srv/workspace-release-set/current/bin/workspace updates:auto configure /etc/workspace/update-schedule.json
php /srv/workspace-release-set/current/bin/workspace updates:auto enable
php /srv/workspace-release-set/current/bin/workspace updates:auto status
php /srv/workspace-release-set/current/bin/workspace updates:auto run
php /srv/workspace-release-set/current/bin/workspace updates:auto pause
php /srv/workspace-release-set/current/bin/workspace updates:auto resume
php /srv/workspace-release-set/current/bin/workspace updates:auto skip 1.3.3
php /srv/workspace-release-set/current/bin/workspace updates:auto unskip 1.3.3
php /srv/workspace-release-set/current/bin/workspace updates:auto disable
```

`configure` сохраняет политику, но отключает автоматику; `enable`/`resume` — явное согласие. `pause` и `disable` не прерывают миграцию в процессе; общая блокировка не позволяет менять политику параллельно с установкой. `skip` исключает конкретную версию до `unskip`; при пропущенном новейшем выпуске не выбирается более старый автоматически. Окно вычисляется в IANA timezone; дни 1–7 (понедельник–воскресенье) обозначают день начала окна, ночное окно продолжается на следующий день. Переход на летнее время следует локальным часам, оба повторённых интервала осенью допустимы; завершение одной установки не дублируется. Проверка выполняется внутри окна, перед quiesce повторно проверяется время и пилотный допуск; начатая операция не прерывается по окончании окна.

Пример `/etc/systemd/system/workspace-update.service` (полномочия, окружение и пути подготовить заранее):

```ini
[Unit]
Description=Workspace automatic update tick
[Service]
Type=oneshot
User=workspace-operator
EnvironmentFile=/etc/workspace/operator.env
ExecStart=/usr/bin/php /srv/workspace-release-set/current/bin/workspace updates:auto run
TimeoutStartSec=6h
```

`/etc/systemd/system/workspace-update.timer`:

```ini
[Unit]
Description=Check Workspace update maintenance window
[Timer]
OnCalendar=*:0/5
Persistent=false
Unit=workspace-update.service
[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now workspace-update.timer
journalctl -u workspace-update.service
```

Не включайте scheduler unit в список останавливаемых юнитов. Не добавляйте `WORKSPACE_UPDATE_MAINTENANCE_TOKEN`, `WORKSPACE_UPDATE_SCHEDULE_TOKEN` или токен издателя в `operator.env`. Общее состояние и `schedule.lock` находятся в WORKSPACE_UPDATE_STATE_DIR; ручные команды проверки/плана/установки также блокируются во время tick. Установщик сохраняет собственную блокировку доступа к данным. Не удаляйте lock-файлы. Ручное вмешательство после завершения tick допускается только после разбора журнала.

### Пилот и сбои

Пилот сначала реально проходит скачивание, план, резервирование, миграцию, переключение, finish и hooks. Статус `pilot_healthy` не разрешает распространение автоматически. После наблюдения и проверки оператор пилота утверждает именно этот выпуск:

```bash
php /srv/workspace-release-set/current/bin/workspace updates:auto approve /secure/pilot-private.pem
```

Команда повторно проверяет журнал завершённого перехода, активную версию, pin релиза и health. Записывает атомарный подписанный допуск `<metadata-sha256>.json` в общий каталог. Follower до установки проверяет подпись закреплённым pilot key, точную идентичность метаданных, пакета, коммита, канала, release pin и возраст (7 суток). Нет допуска — `waiting_for_pilot`. При несовпадении, отзыве или повреждении — также нет установки. При сбое пилота допуск не создаётся; если существовал для повторного пилота, удаляется. При позднем обнаружении проблемы оператор отзывает допуск и ставит пилот на паузу:

```bash
php /srv/workspace-release-set/current/bin/workspace updates:auto revoke METADATA_SHA256
```

Отзыв действует для новых стартов, не отменяет уже начатые операции; каталог должен быть общим, с согласованным чтением, не независимые копии файлов. Пилот не заменяет пять подписей издателя. Автоматический откат БД после открытия записи запрещён. При исключении или прерывании с сохранённым intent (`pending`) scheduler ставит паузу, пытается закрыть ingress/писателей и показывает этап, требующий восстановления. Повторный tick не запускает миграции автоматически. Если `recovery_quiesce_failed`, немедленно вручную остановите все писатели и проверьте отзыв допуска. Используйте `updates:status`, ручной install/finish/rollback с прежними параметрами и RECOVERY.md. После finish возможны новые операции; не восстанавливайте старую БД без сверки. После ручного проверенного восстановления и снятия маркера оператор выполняет `updates:auto ack-recovery` (остаётся на паузе), затем `resume` при отдельном решении. Полная production-приёмка требует испытать реальные hooks, timer, два узла, оба канала, отзыв допуска, отказ на каждом этапе, DST и проверочное восстановление на выбранной СУБД.
