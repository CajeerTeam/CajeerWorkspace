# 0.9.0 — Пилот двух команд

Этот этап не изменяет схему 33. Он поставляет операционные команды для создания реальных пользователей и проектов и проверки стенда. Не запускайте пилот в production: отдельные БД, файловое хранилище, сервисные аккаунты, тестовые домены и тестовый репозиторий обязательны. Никаких заранее установленных паролей, автоматической публикации OSS или поддельных подтверждений провайдеров.

## 1. Подготовка

Создайте чистую установку, только одного владельца через `php bin/workspace init EMAIL "Owner"` (пароль из stdin). До `pilot:seed` не выполняйте `sync`. Сохраните приватную конфигурацию вне docroot, задайте `WORKSPACE_CONFIG`, `WORKSPACE_DATA`, `WORKSPACE_MFA_KEY`, настройки OIDC и `WORKSPACE_PILOT=1`. В конфигурации `_stand.environment` должен быть `staging`, владелец стенда задан. Настройте ровно один экземпляр каждого из девяти типов: Engine, Logs, Forum, Book, Lite, Bots, Servers, aaPanel, GitHub. Укажите ответственного и `launch_url` каждого, для GitHub — `repository` реального выделенного тестового OSS-репозитория. См. `config/connections.example.json` и `docs/INTEGRATIONS.md`. Не используйте production-ключи. Специализированные конфигурации модулей (GitHub App, Forum identities, Lite targets, Logs, Bots, Sign и т.д.) настраиваются отдельно по их документации; привязка каталога не означает, что эти действия разрешены или готовы.

## 2. Развёртывание

Сформируйте приватный JSON с полями `organization`, `internal`, `client`, `oss`, `client_name`, `oss_slug`, `staff`. Первые шесть полей — строки (названия, название клиента, уникальный slug OSS). `staff` — объект с ровно восемью ключами: `lead`, `developer`, `client_manager`, `client_developer`, `accountant`, `legal`, `legal_reviewer`, `operator`. Каждый содержит `email`, `name`, `password` (12–72 байта, уникальный пароль). Адреса должны быть реальными отдельными тестовыми аккаунтами. Для OIDC привяжите каждый к своему `subject` штатным `auth:bind`. Установите права 0600 на входной файл; не храните его в репозитории, логах или артефактах CI.

```sh
php bin/workspace doctor
php bin/workspace pilot:seed OWNER_ID < /secure/pilot-input.json > /secure/pilot-layout.json
```

Команда создаёт две команды, три проекта, восемь сотрудников, их членство, OSS-профиль (не опубликован), двойной контроль платежей клиентского проекта и связи девяти подключений в одной транзакции. Возвращает только ID, без паролей. Повтор запрещён, существующие установки не изменяются. При ошибке вся операция откатывается. Удалите входной файл после безопасной передачи паролей. Не переназначайте пароль владельца из файла.

| Учётная запись | Internal | Client | OSS |
| --- | --- | --- | --- |
| Owner | owner | owner | owner |
| lead | manager | — | manager |
| developer | developer | — | developer |
| client_manager | — | manager | — |
| client_developer | — | developer | — |
| accountant | — | accountant | — |
| legal | — | legal | — |
| legal_reviewer | — | legal | — |
| operator | operator | — | operator |

Каталог: Engine, Logs, Servers, aaPanel, GitHub — internal и OSS; Book, Forum, Lite, Bots — OSS. Клиентский проект по умолчанию не получает технические подключения. Это только каталог, не разрешение внешнего API. Репозиторий GitHub App привязывайте к OSS-проекту, а не одновременно к двум проектам. Если нужны отдельные подключения клиентского проекта, используйте отдельный профиль после завершения этой проверки.

Гость: владелец или юрист загружает реальный тестовый PDF в клиентском проекте; владелец выдаёт приглашение на конкретную редакцию (или заказ) штатным интерфейсом или CLI: `php bin/workspace pilot:guest OWNER_ID DOCUMENT_ID REVISION HOURS [ORDER_ID] < /secure/guest-email.txt > /secure/guest-token.txt`. Установите `umask 077` перед редиректом, токен одноразовый и не включается в отчёт. Гость входит через SkiF4er ID с подтверждённым отдельным email. Не создавайте его как сотрудника. Настройка OIDC: `AUTHENTICATION.md`; заказ/гость: `CLIENTS.md`. Отозванный или истёкший гость не считается активным.

## 3. Фактическая проверка стенда

```sh
php bin/workspace pilot:check OWNER_ID > /secure/pilot-topology.json
php bin/workspace pilot:probe OWNER_ID > /secure/pilot-readiness.json
php bin/workspace sync
php bin/workspace profile --check
```

`pilot:check` сверяет проектную матрицу актуальным RBAC, привязки и их исходные хеши целей, репозиторий, двойной контроль, активный гостевой grant и хеш его PDF. Код 1, если нет действующего гостя или структура отличается. `pilot:probe` делает новые независимые проверки девяти API; код 1 при недоступности, архивном GitHub, неизвестной версии или несовпадении версии. `declared_version_only` означает готовность API и операторскую версию, а не подтверждение версии через API. Ошибки не содержат тела ответов или ключей. `sync` дополнительно сохраняет штатный журнал переходов. Probe не является проверкой возможности публикации или доставки.

## 4. Четыре сценария приёмки

`python3 tools/pilot.py --lite-source /path/to/EngineLite` выполняет регрессионные группы на отдельных временных БД с тестовыми транспортами. Для Lite задайте `WORKSPACE_LITE_TEST_SOURCE` на закреплённый EngineLite 1.6.0. Отчёт содержит версию Workspace, SHA-256 каждого теста, код завершения и длительность; он не подменяет живой протокол. Повторять на реальном стенде вручную по следующим связям, записывая ID входов, исходов, версии, время и роль (не секреты):

1. Владелец оформляет запрос и смету (коммерческие операции в текущей версии доступны только владельцу), менеджер координирует задачи; гость подтверждает её, исполнитель ведёт задачу и часы, юрист готовит акт, бухгалтер выпускает счёт и проводит частичный/полный платёж, владелец согласует платежи; сверить выписку. Проверить, что другой разработчик не видит объект.
2. Поставка продукта на OSS-проекте (GitHub App может привязать один репозиторий только к одному проекту): задача, PR, CI, release SHA, staging, отдельное production-подтверждение **внутри тестового окружения**, Servers/aaPanel, Logs trace. Не направлять деплой на реальный production. Проверить отказ отдельного провайдера и безопасное восстановление.
3. OSS: issue, PR, review, зафиксированная подборка Book, публикация Engine и отдельно Lite, тема Forum, одно уведомление Bots. Публиковать только в выделенном тестовом канале и репозитории. Не повторять неизвестную доставку.
4. Client: две редакции договора, согласование с тремя разными участниками (legal, legal_reviewer и owner), Dropbox Sign только TEST, архив, утверждённый акт, проводка, закрытие периода. Проверить отзыв доступа, сторно и целостность восстановленного PDF.

Для каждого сценария отдельно зафиксировать успешный результат и отказ одного поставщика. Не закрывать приёмку по одному readiness-ответу. Живые испытания требуют реальных настроек, подтверждений пользователей и отдельной подписи владельца. После проверки удалить/отозвать тестовые ключи, приглашения и отключить `WORKSPACE_PILOT`; хранить отчёты в защищённом каталоге. Следующий этап 0.9.1 — измерение RTO/RPO и нагрузки.
