# 1.2.0 — GitHub Release Distribution: регламент допуска и сопровождения

Версия кода 1.2.0, замороженная схема 36. **Номер версии не равен допуску стенда.** `tools/release.py` собирает воспроизводимый полный ZIP с `SHA256SUMS` и внешним `.sha256`, но не публикует официальный релиз. `tools/production.py` проверяет отчёты, собирает протокол, проверяет пять подписей и выпускает подписанный пакет только после выполнения всех условий. Он не управляет внешними сервисами, не делает юридических заявлений, не проверяет реальность ручных аттестаций вместо участников. GitHub Actions публикует только неподписанный кандидат. Патч-архив изменений исходников сам по себе не является полным подписанным дистрибутивом.

## 1. Матрица и ответственность

Требования к runtime: 64-bit PHP 8.3+ (<9), PDO, выбранный PDO-драйвер, session, OpenSSL, cURL с HTTPS. CI-матрица PHP 8.3/8.4/8.5, SQLite 3.27+ или PostgreSQL 14/16 для утверждаемого production-профиля. Для операций выпуска/восстановления Linux/POSIX, Python 3.9+, OpenSSL CLI, для PG — соответствующие утилиты `pg_dump`/`pg_restore`. Это целевые версии приёмки, не утверждение, что CI уже зелёный. Для любого расширения матрицы нужен новый проверяемый выпуск.

| Подключение | Версия / контракт | Обязательные возможности | Роль сопровождающего |
| --- | --- | --- | --- |
| Engine | 2.1.0 | Редакции, публикация, сверка | Тимлид |
| Logs | 1.1.1 | Ingest, correlation, retention, сверка | Дежурный |
| Forum | Edition 1.6.0 / Core 2.1.0 | ACL, темы, модерация, сверка | Тимлид |
| Book | 1.2.0 | Публичный Reader, неизменяемый снимок, review | Тимлид |
| Lite | 1.6.0, native schema 14 | Локальная публикация, backup/restore, конфликт редакций | Дежурный |
| Bots | 1.0.2 + обязательный патч в integrations/ | workspace-delivery-v1, подтверждение, очередь/отмена, сверка | Дежурный |
| Servers | 1.0.2 | Чтение Inventory, сигнал инцидента | Дежурный |
| aaPanel | Точная версия стенда, не произвольный диапазон | Inventory, сигналы сайта и SSL | Дежурный |
| GitHub | REST API 2026-03-10, SaaS | Репозиторий, App webhook, PR/CI, SHA выпуска | Тимлид |

Машиночитаемая матрица `config/compatibility.json` включена в полный ZIP и закреплена его контрольными суммами. `draft` заполняет матрицу наблюдавшимися/объявленными версиями и хешами целей из `pilot:probe`, а возможности оставляет **false** до живого теста. GitHub — версия API, не версия SaaS. `operator_attested` означает версию, проверенную оператором в самой установке, если API её не выдаёт; не выдавать её за удалённо наблюдавшуюся. Применить патч Bots и проверить новый API и worker на одном и том же коде. Проверять каждый отдельный экземпляр, дополнительные экземпляры не считаются принятыми этим протоколом. Не пересылать ключи и ответы API с персональными данными в отчёт.

Пять подписантов протокола и их обязанности: владелец продукта — бизнес-допуск и список дефектов; тимлид — код, CI, проектная изоляция, локализация, обновление и контракт интеграций; бухгалтер — сверка денег по валютам, проводки и применимость налогового профиля; юрист — документы, полномочия, гостевой доступ, допустимость провайдера подписи; дежурный — RTO/RPO, мониторинг, доступность, восстановление и запуск worker. Назначить также конкретного сопровождающего Workspace, релизного процесса, безопасности, базы, финансов, юридических документов и каждого из девяти подключений, а также резервного дежурного и контактный канал в защищённом операционном журнале. Имена в `review.json.owners` заполняются из реального реестра подписантов при создании черновика; заменить их на фактических ответственных, если отличается распределение. Отсутствие имени блокирует допуск. Не использовать фиктивные имена из тестов. Выпускающий ключ — отдельный от пяти ключей согласования.

Налоговые профили: `management_cash_only` (управленческий кассовый/двойной учёт, не полный statutory accounting), `uk_sole_trader_standard_vat_b2b_gbp` (только границы [UK_VAT.md](UK_VAT.md)). Провайдер `dropbox_sign_v3` — строго [SIGNING.md](SIGNING.md), не QES. Выбрать профиль по согласованию с бухгалтером и юристом; остальные юрисдикции/провайдеры не входят в данный допуск.

## 2. Доверенные ключи

Оператор создаёт закрытые каталоги вне кода, данных и docroot. Реестр `/secure/release-trust/trust.json` содержит ровно шесть полей `product_owner`, `team_lead`, `accountant`, `lawyer`, `on_call`, `release`. Каждое — объект с `identity` (реальное имя/уникальная идентичность) и `sha256` (64 hex SHA-256 точных байтов соответствующего `<role>.pub.pem`). Файлы PEM с публичными ключами находятся рядом с реестром. Проверить идентичность каждого владельца ключа по независимому каналу. Все шесть ключей различны (сравнивается нормализованное DER), пять подписантов — разные люди. Поддержаны RSA >=2048 или именованные EC prime256v1/secp384r1/secp521r1. Закрытые ключи хранятся раздельно у владельцев с правами 0600 или строже; не передавать их в репозиторий, CI или на веб-сервер. Использовать зашифрованные PEM с интерактивным вводом пароля. Вычислить и независимо зафиксировать `TRUST_SHA256` после утверждения реестра; не брать его из скачанного неподтверждённого пакета. Хранить исторический реестр и pin вместе с протоколом для проверки старых выпусков. При ротации/компрометации остановить выпуск, утвердить новый реестр, повторить согласования; доверие к старой подписи после компрометации решается отдельно.

## 3. Живые доказательства

Сначала выполнить CI на точном коммите (PHP verify, postgres, bots-compatibility, recovery-postgres, release-rehearsal, package). Взять именно собранный ZIP и `.sha256`, сверить с CI artifact, сохранить SHA-256 независимо. Проверять CI по журналу конкретного run/commit; `review` содержит аттестацию участников, инструмент не делает запросы к GitHub Actions. Прежний полный пакет 1.1.2 сохранить с доверенным SHA-256, не использовать архив изменений вместо полного пакета. Сборка на доверенном checkout:

```sh
python3 tools/release.py build --output /secure/dist
python3 tools/release.py verify /secure/dist/CajeerWorkspace-1.2.0.zip
(cd /secure/dist && sha256sum -c CajeerWorkspace-1.2.0.zip.sha256)
```

Развернуть кандидат на **изолированном** стенде по [PILOT.md](PILOT.md). Настроить девять отдельных тестовых подключений и отдельные роли. Проверить чистую установку, четыре сквозных сценария, отклонение неавторизованных действий, локализацию, каждый capability в матрице, реальные отказы. Проверить все политики входа, смешанный вход одной записи, смену организации с повторным OIDC, отзыв сессии и свежий MFA (`auth_policy` в checks). Провести репетицию 1.1.2→1.2.0 и возврата на копии данных и проверить восстановление по [RECOVERY.md](RECOVERY.md). Согласовать заранее объём нагрузки и пороги p95/RTO/RPO; сохранять реальный протокол остановки worker, рестарта БД, переноса площадки и ротации ключей. RTO в отчёте инструмента — время от объявленного отказа до *проверенного офлайн-восстановления*, дополнительно измерить время возвращения сервиса и сравнить с согласованным service RTO. RPO — возраст контрольной точки в момент отказа, не оценка потерянных транзакций. Не подставлять показатели тестового HTTP-сервера. При закрытии критических дефектов повторить соответствующие проверки. Документы с персональными данными хранить отдельно, в протоколе — ссылки/идентификаторы и хеши доказательств.

Приватный каталог `/secure/evidence` (0700), `umask 077`, команды на кандидате 1.2.0 (проверять exit status каждой):

```sh
php bin/workspace auth:acceptance > /secure/evidence/realm-observed.json
php bin/workspace pilot:check OWNER_ID > /secure/evidence/topology.json
php bin/workspace pilot:probe OWNER_ID > /secure/evidence/readiness.json
python3 tools/load.py --staging --profile /secure/load-profile.json > /secure/evidence/load.json
# Сохранить RESTORE-REPORT.json из выполненного restore с --outage-at:
cp /srv/pilot-recovered/RESTORE-REPORT.json /secure/evidence/restore.json
```

`restore.json` должен содержать `outage_to_verified_restore_seconds` и `backup_age_at_outage_seconds`, подтверждение карантина и совпадения остатков, проводок, областей доступа и очередей. Не вводить цифры вручную вместо отчёта. Проверить, что backend/версии и исходные данные соответствуют пилоту. `pilot:check` требует действующего гостя и актуальной топологии, `pilot:probe` — девять готовых подключений. `load` проверяется суммарно и по каждому маршруту.

```sh
ARCHIVE=/secure/dist/CajeerWorkspace-1.2.0.zip
EVIDENCE=/secure/evidence
TRUST=/secure/release-trust
# TRUST_SHA256 и PREVIOUS_SHA256 предварительно получены независимо
python3 tools/production.py draft --archive "$ARCHIVE" --evidence "$EVIDENCE" \
  --previous-sha256 "$PREVIOUS_SHA256" --trust "$TRUST" --trust-sha256 "$TRUST_SHA256"
```

`review.json` — черновик, а не положительный отчёт. Заполнить `stand`, `checked_at` (ISO 8601 с часовым поясом после завершения проверок), `tax_profile`, `signature_provider`, `php_version` (например 8.4.24), `database_version` (точная версия), `owners`. `integrations` содержит `version`, `target_hash`, `version_evidence`, `capabilities` (по одному флагу на каждую проверку) и `evidence_ref` (проверяемый ID/ссылка или SHA-256 подробного протокола); сохранить фактические версии и хеши, подтвердить проверенные возможности. `scenarios`: client, delivery, oss, legal_finance. `checks`: clean_install, upgrade, rollback, auth_policy, identity_sessions, realm_acceptance, rbac, localization, worker_loss, database_restart, offsite_restore, key_rotation. Для `identity_sessions` приложить результаты привязки через реальный ID, отвязки, отзыва отдельной сессии и восстановления в обязательном SSO. Для `realm_acceptance` приложить успешный JSON `auth:acceptance` и отдельные реальные доказательства ручных проверок из AUTHENTICATION.md (RP logout, ротация ключа realm, отказ и восстановление, изоляция клиента, отключение аварийного флага). Только после этого отмечать `passed`. Для каждого указать `passed` и `evidence_ref` (реальный протокол с временем, участниками и результатами). `ci`: `run`, 40 hex `commit`, `jobs` с `success` только для реально успешных заданий. `thresholds`: `minimum_requests`, `minimum_concurrency`, `p95_ms`, `error_rate` (0..1), `rto_seconds`, `rpo_seconds`. Указать `open_critical_defects` целым числом; требуется 0. Допуск проверяет соответствие reports, выбранных версий, порогов и подписей; утверждение ручных проверок остаётся ответственностью пяти участников, а не симуляцией внешней проверки.

## 4. Подпись и выпуск

Согласование и публикация допускаются в течение семи дней после проверки; readiness/topology должны быть не старше семи дней на дату review. При изменении отчёта или пакета создать новый комплект доказательств и собрать все подписи заново. `assemble` создаёт канонический `acceptance.json` с хешами точного пакета, прежнего выпуска, матрицы, реестра и всех пяти отчётов; не перезаписывает существующий протокол.

```sh
python3 tools/production.py assemble --archive "$ARCHIVE" --evidence "$EVIDENCE" \
  --previous-sha256 "$PREVIOUS_SHA256" --trust "$TRUST" --trust-sha256 "$TRUST_SHA256"
# Каждый участник отдельно, после чтения всех доказательств, с собственным ключом:
python3 tools/production.py approve --archive "$ARCHIVE" --evidence "$EVIDENCE" \
  --role product_owner --private-key /secure/owner-private.pem \
  --trust "$TRUST" --trust-sha256 "$TRUST_SHA256"
# Аналогично: team_lead, accountant, lawyer, on_call (отдельные ключи).
python3 tools/production.py publish --archive "$ARCHIVE" --evidence "$EVIDENCE" \
  --private-key /secure/release-private.pem --output /secure/releases/1.2.0 \
  --trust "$TRUST" --trust-sha256 "$TRUST_SHA256"
python3 tools/production.py verify --bundle /secure/releases/1.2.0 \
  --trust "$TRUST" --trust-sha256 "$TRUST_SHA256"
```

Папка `/secure/releases` должна быть существующей приватной папкой; целевая папка — новой. Перед публикацией копируются и проверяются точные байты, проверяются пять подписей, затем отдельный release key подписывает полный ZIP и `acceptance.json`; проверяется весь комплект до атомарной смены каталога. Подписанный архив, `.sha256`, `.sig` можно распространять отдельно для проверки доверенным публичным ключом и его pin; полный протокол (включая отчёты и пять `.sig`, `release.sig`) хранить ограниченно. `verify` проверяет исторический протокол без истечения его срока; это не подтверждение текущей готовности сервиса. Не распространять закрытые ключи, входные файлы пилота или секреты. Не доверять автоматически публичному ключу из пакета. Обычная `candidate.py sign/prepare` — низкоуровневые команды для репетиции, не акт production-приёмки. При подготовке стенда 1.2.0 для сбора доказательств допустима тестовая подпись и низкоуровневый переключатель; никогда не распространять её как официальную.

## 5. Обновление 1.1.2 → 1.2.0 и возврат

Остановить **все** HTTP/FPM/CLI, cron, worker и другие процессы записи. Обеспечить исключение параллельной старой площадки; флаг не останавливает процессы. Доверенная копия инструмента 1.2.0, отдельный приватный каталог релизов, код только на чтение для runtime, конфигурации/ключи/данные/объекты вне кода. Сохранить настройки, версии ключей, код и конфигурацию предыдущего релиза отдельно. Пример SQLite; для PostgreSQL использовать `WORKSPACE_DB=pgsql`, явные PG-параметры и `--backend pgsql`, без `--data` у backup, проверить отдельный restore. Не переносить старые сессии и lock-файлы между площадками.

```sh
export WORKSPACE_RECOVERY_OFFLINE=1
# Из исходного 1.1.2:
python3 tools/recovery.py backup --backend sqlite --data /srv/workspace-data \
  --objects /srv/workspace-objects --destination /secure/pre-110
# Сохранить manifest_sha256 независимо как BACKUP_SHA256; проверить restore отдельно.
# Из доверенного 1.2.0:
python3 tools/production.py prepare --bundle /secure/releases/1.2.0 \
  --root /srv/workspace-release-set --previous /secure/previous/CajeerWorkspace-1.1.2.zip \
  --trust "$TRUST" --trust-sha256 "$TRUST_SHA256"
python3 tools/production.py upgrade --bundle /secure/releases/1.2.0 \
  --root /srv/workspace-release-set --backup /secure/pre-110 --backup-sha256 "$BACKUP_SHA256" \
  --data /srv/workspace-data --objects /srv/workspace-objects \
  --trust "$TRUST" --trust-sha256 "$TRUST_SHA256"
```

Подготовка привязывает точный предыдущий архив к протоколу и проверяет подписи. Переключение проверяет оба дерева и полное логическое состояние схемы 36 средствами доверенных версий 1.1.2 и 1.2.0. Миграций нет; данные, денежные остатки, объекты и очереди должны совпасть с исходным снимком. Только затем атомарно меняется `current`. При отказе держать все процессы записи выключенными до проверки и восстановления.

**Возврат не является переключением только кода.** Схема 36 одинакова, но возврат допускается только при совпадении состояния с проверенным снимком. Остановить процессы, отдельно сохранить и проверить актуальную копию 1.2.0, включая политики и внешние эффекты. Согласовать, что возвращаемый снимок 1.1.2 не теряет новые записи, либо выполнить контролируемое восстановление со сверкой на отдельной площадке. Использовать `tools/recovery.py restore` из доверенной версии 1.1.2, а не из 1.2.0; снять карантин только по процедуре RECOVERY.md соответствующей версии. После проверенной замены данных/объектов в ранее зафиксированном пути (для PG — прежняя согласованная цель) и восстановления конфигурации выполнить команду `production.py rollback` с прежними аргументами. Инструмент принимает только точное логическое состояние исходного снимка схемы 36, не удаляет таблицы и не переписывает базу. До репетиции возврата не включать запись. Не менять SQL 001–036, не уменьшать номер схемы вручную. Хранить прежний ключ MFA и сверять уже совершённые внешние действия.

После проверки переключить docroot на `current/public`, перезапустить FPM/OPcache, проверить HTTPS, health, сессии, MFA, чтение защищённых страниц, хеши документов и деньги. Включать worker по одному после сверки исходящих и неизвестных операций; не повторять неизвестные отправки. Допуск конкретной площадки подтверждают владельцы после smoke. `service_ready=false` от инструмента означает, что сам он не запустил сервис.

## 6. Сопровождение

Дежурный наблюдает health, SLA инцидентов, очередь/lease, DLQ, возраст последней проверенной копии, доступность девяти подключений и ошибки Logs; проверяет после обновления и регулярно по согласованному SLA. Ответственный за базу выполняет расписание проверенных offsite-копий по RPO, пробное восстановление и проверку RTO; копии, включая ключи и конфигурацию, защищаются отдельно (инструмент не шифрует их). Release owner фиксирует коммит, пакет, подпись и приёмку, обрабатывает ротацию и отзыв ключей. Тимлид проверяет обновления сторонних API на стенде; новая версия интеграции не становится автоматически совместимой. Бухгалтер сверяет валютные остатки и закрытие периода; юрист проверяет целостность оригиналов, сроки хранения, отзыв гостя и провайдера подписи. При критическом нарушении денег, документов, доступа, неизвестной доставке или невозможности отката — остановить соответствующую запись, зарегистрировать инцидент, сохранить доказательства, известить владельца, восстановить или исправить, повторить приёмку. Перед плановыми обновлениями согласовать окно, backup, rollback и владельцев, оповестить команду. Подтверждение CI не заменяет живой протокол.

Публикация в GitHub Releases выполняется отдельным инструментом после закрытого допуска, по [WORKSPACE_UPDATES.md](WORKSPACE_UPDATES.md).
