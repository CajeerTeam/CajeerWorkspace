# Авторизация, MFA и клиентский кабинет · 1.1.1

## Обновление

Схема 006 для SQLite и PostgreSQL добавляет идентичности, TOTP, аварийные учётные записи, клиентские приглашения, реестр OIDC-сессий и события отзыва. SQL 001–005 не изменены. Перед `upgrade` остановите приложение/cron, сохраните код, конфигурацию и проверенную копию БД; PostgreSQL — `pg_dump` и проверка восстановления. После обновления старые PHP-сессии недействительны. Следуйте [UPGRADE.md](UPGRADE.md).

## Политики входа в 1.1.0

Администратор установки задаёт `WORKSPACE_AUTH_POLICY` в окружении FPM и CLI (одинаковое значение на всех узлах). При явном значении оно имеет приоритет над прежним `WORKSPACE_OIDC_REQUIRED` и наличием настроек клиента; удалите устаревший флаг после перехода. Не задавайте смешанный режим, если ранее требовался обязательный SSO и это требование остаётся в силе. Неизвестное значение блокирует авторизацию с 503. При отсутствии или пустом значении действует **точно прежний выбор режима**: required при `WORKSPACE_OIDC_REQUIRED=1` или непустом ID/секрете клиента, иначе local. Не происходит автоматического понижения до local при ошибке провайдера.

| Установка | Организация наследует | Организация требует ID |
| --- | --- | --- |
| `local` — локальный вход | Только пароль | Нет допустимых методов, доступ закрыт |
| `mixed` — локальный + SkiF4er ID | Пароль или ID | Только ID |
| `required` — обязательный SkiF4er ID | Только ID; предусмотрен прежний аварийный вход | Только ID, без аварийного исключения |

На схеме 34 отсутствие строки политики означает наследование; обновление со схемы 33 не меняет пароли, идентичности, членство или текущие настройки окружения. Не переносите старые файлы сессий при восстановлении. Смена режима установки действует на очередном запросе: локальная сессия при required и OIDC-сессия при local прекращаются. В `mixed` обе формы доступны одновременно. Сотрудник входит в одну запись по паролю и ранее привязанному `issuer + sub`; автоматической привязки по почте нет. В 1.1.1 пользователь смешанного режима может самостоятельно привязать ID в разделе «Безопасность».

- Перед изменением режима запускайте `php bin/workspace auth:policy` с предполагаемым окружением на staging. Отчёт показывает наследование, эффективную политику, количество активных привязанных владельцев и конфликты; код 1 при закрытой организации или отсутствии привязанного владельца в required. Затем `php bin/workspace auth:check` проверяет MFA и настройку/доступность OIDC. Ни одна команда не подтверждает успешный живой вход.
- Владелец организации входит через ID, подтверждает TOTP в «Безопасности», в «Команда → Политика авторизации» выбирает «Обязательный SkiF4er ID» или возврат к наследованию. Операция защищена CSRF, ролью владельца, свежим MFA и записывается в аудит. Организация не может разрешить методы, которые запретила установка. В local настройка ужесточения недоступна.
- Парольный вход в mixed выбирает первую доступную организацию; если все требуют ID, парольный вход отклоняется. При выборе SSO-организации локальной сессией запускается новый OIDC Authorization Code + PKCE с `prompt=login`, привязкой к исходному UID/версии сессии/целевой организации. Callback принимает только тот же связанный UID с текущим членством. Старый MFA не переносится, токены и CSRF обновляются. Неверный субъект, отозванное членство, истекшая транзакция или отказ IdP не открывают целевую организацию. Старая разрешённая организация остаётся доступна, если исходная сессия ещё действительна.
- Локальная регистрация/принятие приглашения не обходит политику целевой организации. Для приглашения SSO используйте «Принять через SkiF4er ID»; существующая запись должна быть привязана оператором. Приглашения клиентов через ID сохраняются в mixed/required; contributor и публичные ссылки остаются отдельными ограниченными механизмами, не предоставляющими членство сотрудника.
- При local поверх организаций с явным required система не ослабляет их политику. Верните mixed/required и восстановите доступ через проверенный ID владельца; при отсутствии привязки используйте операторский `auth:bind` после проверки субъекта. Прежде чем переводить установку в local, снимите явные требования ID через владельцев в режиме с доступным ID. Смена политики проверяется на каждом защищённом запросе и при доменной авторизации.

Проверки: `php tests/auth_policy.php`, `php tests/auth_db.php`, `python3 tests/auth_policy_e2e.py`; сценарий переноса политики также выполняется в `auth_db.php --postgres`. Для реальной приёмки дополнительно проверьте два способа входа одного пользователя, переход в SSO-организацию, другой субъект, отказ IdP, отзыв членства и повторный MFA на реальном realm. Используйте только тестовый confidential client.

## Настройка SkiF4er ID

Используется серверная реализация OIDC на PHP/OpenSSL/cURL в соответствии с [SDK Center](https://id.skif4er.ru/sdk/). Официальный issuer фиксирован: `https://id.skif4er.ru/realms/skif4er`. Discovery, JWKS, token, introspection и logout запрашиваются по HTTPS на этом issuer; редиректы при backend HTTP-запросах запрещены. Требуется реальный confidential client в realm `skif4er`.

1. В Keycloak зарегистрируйте клиент, например `cajeer-workspace`, включите Standard Flow, Client authentication, PKCE S256. Отключите Implicit Flow, Direct Access Grants и Service Accounts (если не используются). Установите ID Token Signature Algorithm RS256, client_secret_basic. Scopes `openid profile email`; для приглашений нужен `email_verified=true` в ID token. Настройте точные URI для установки (без `*`), например:
   - Valid redirect URI: `https://workspace.example.com/?p=oidc.callback`
   - Valid post logout redirect URI: `https://workspace.example.com/?p=login`
   - Backchannel logout URL: `https://workspace.example.com/?p=oidc.backchannel`; Backchannel logout session required: On.
2. Сгенерируйте отдельный ключ шифрования TOTP (`openssl rand -hex 32`). Храните его в менеджере секретов и резервируйте отдельно от БД. Одинаковый ключ нужен CLI и FPM, в том числе после переноса SQLite → PostgreSQL. Потеря ключа означает необходимость операторского сброса MFA; произвольная замена ключа не выполняет ротацию существующих секретов.
3. Настройте переменные окружения приложения, включая FPM (не передавайте секреты в shell history, URL, Git или публичный файл):

```text
WORKSPACE_PUBLIC_URL=https://workspace.example.com/
WORKSPACE_AUTH_POLICY=mixed
WORKSPACE_OIDC_CLIENT_ID=cajeer-workspace
WORKSPACE_OIDC_CLIENT_SECRET=<секрет Keycloak>
WORKSPACE_MFA_KEY=<64 шестнадцатеричных символа>
WORKSPACE_HTTPS=1
WORKSPACE_EMERGENCY_LOCAL=0
```

`WORKSPACE_PUBLIC_URL` — точный внешний HTTPS URL каталога приложения с завершающим `/`. Не берётся из Host/X-Forwarded-Host. При `WORKSPACE_AUTH_POLICY=required` локальный вход не включается при отсутствии client secret/ID; вход OIDC не произойдёт до исправления. В mixed парольный доступ остаётся только для организаций, допускающих пароль. Для reverse proxy передавайте HTTPS только из доверенной конфигурации; отключите открытый HTTP на стороне пользователя, настройте HSTS и TLS. Cookies Secure, HttpOnly, SameSite=Lax. Не записывайте query callback (authorization code/state), тело POST backchannel, Authorization, содержимое сессий или секреты в журналы; настройте журналирование reverse proxy соответственно. Каталог `WORKSPACE_DATA` и PHP-сессии должны быть недоступны из web и другим пользователям ОС. Защищайте резервные копии.

4. Проверьте `php bin/workspace doctor` и `php bin/workspace auth:check`. Последняя команда проверяет формат ключа MFA, настройку клиента и discovery, не печатает секреты. Она не выполняет пользовательский вход и не подтверждает client secret у провайдера.
5. Для существующего владельца оператор сначала получает достоверный `sub` из Keycloak Admin Console (не username/email) и привязывает его:

```sh
php bin/workspace auth:bind owner@example.com '<проверенный-sub>'
```

Привязка однозначна по `iss + sub`. Даже подтверждённый email не привязывает существующего пользователя автоматически. Для замены привязки используйте атомарный `auth:recover EMAIL VERIFIED_SUBJECT TICKET`. `auth:unbind EMAIL` требует подтверждённого локального пароля через stdin и не разрешён при обязательном ID. Эти команды отзывают прежние сессии. Нельзя назначить один активный subject одновременно сотруднику и гостю. Новые сотрудники могут принять обычное организационное приглашение через ID с совпадающей подтверждённой почтой: только тогда создаётся привязка и членство. Существующий локальный пользователь может привязать ID самостоятельно в mixed либо обратиться к оператору. Не выдавайте владельца приглашением без проверки полномочий.

## Сессии и выход

Вход: серверная одноразовая транзакция 5 минут с state, nonce и PKCE S256, затем обмен кода через confidential client. Проверяются подпись RS256 по актуальному JWKS (новый kid при ротации), issuer, audience, azp, iat/exp/nbf, nonce. Токены хранятся только в приватной PHP-сессии; браузер получает непрозрачный session cookie. После входа и MFA ID cookie меняется. Access token проверяется через introspection при входе и не реже одного раза за 30 секунд при защищённых запросах; refresh выполняется сервером перед истечением. Ошибка, отзыв или неизвестная идентичность прекращают локальный доступ. При пользовательском выходе локальная сессия отзывается, затем выполняется RP logout. Backchannel проверяет подпись/issuer/audience/events/iat/jti, отзывает только подходящие sid/sub и сохраняет кратковременный журнал для защиты от повторной доставки и гонки с callback. Без backchannel задержка обнаружения отзыва — до 30 секунд между проверками плюс уже выполняющийся запрос. При ошибке связи protected request не продолжает работу после требуемой проверки. Сессия ограничена 30 минутами бездействия и 12 часами общего срока.

## Второй фактор

TOTP (RFC 6238 SHA-1, 6 цифр, 30 секунд) не зависит от настроек MFA Keycloak. После входа за первые пять минут откройте «Безопасность», добавьте показанный Base32-секрет в приложение-аутентификатор вручную и подтвердите первый код. Секрет шифруется AES-256-GCM с привязкой к ID пользователя, не записывается в аудит. Повторное использование уже принятого шага запрещено транзакционно; допускается соседний интервал в пределах ±30 секунд. Ограничение попыток — 8 за 10 минут на пользователя. Синхронизируйте часы сервера и телефона. После успешного подключения старые сессии пользователя отзываются.

Подтверждение действует пять минут в конкретной сессии. Обязательно для создания/сторно/решения по платежам, изменения политики согласования, загрузки документов, скачивания внутренних PDF, CSV-экспорта, подключения/отвязки интеграций, изменения ролей/членства/команд/организаций и выдачи/отзыва приглашений. После отказа откройте «Безопасность», подтвердите код и вручную повторите исходный запрос; исходные POST и файлы не сохраняются для автоповтора. Обычный просмотр разрешённых разделов и работа с задачами остаются по RBAC. Гостевая выдача закреплённого PDF защищена отдельной OIDC-сессией и грантом, а не MFA сотрудников.

Сброс при утрате аутентификатора: оператор проверяет личность и выполняет `php bin/workspace auth:mfa-reset EMAIL`, после чего отзываются сессии и пользователь подключает новый фактор. Для аварийной учётной записи сначала снимите разрешение `auth:emergency EMAIL off`. Доступ к CLI — административный; ограничьте OS-права и ведите отдельный журнал действий оператора.

## Аварийный локальный вход

Подготовьте выделенную локальную учётную запись владельца до включения OIDC: установите сильный пароль, войдите в локальном режиме, подключите TOTP и сохраните оба фактора раздельно. Назначьте:

```sh
php bin/workspace auth:emergency emergency@example.com on
```

При недоступности ID оператор разрешает аварийный вход флагом `WORKSPACE_EMERGENCY_LOCAL=1` в окружении FPM (перезапуск/перезагрузка конфигурации). Вход требует пароль и существующий TOTP до открытия любых защищённых разделов. В required проверяется активное членство владельца именно в выбранной организации, наследующей режим установки. Явная политика организации required аварийный вход не допускает. В mixed обычный локальный вход не является аварийным. После восстановления верните флаг `0`, отзовите аварийный доступ при необходимости командой `auth:emergency EMAIL off`. Проверьте этот сценарий в закрытом стенде до включения SSO. В local и разрешённых организациях mixed MFA для чувствительных операций также обязательна.

## Одноразовый клиентский доступ

Владелец клиентского проекта загружает PDF, открывает карточку проекта, выбирает **конкретную редакцию**, email клиента и срок кода (1–168 часов), затем подтверждает MFA. Код 256 бит показывается один раз; в БД — только SHA-256. Передайте код лично по защищённому каналу вместе со ссылкой на `?p=guest.join`. Код не включается в URL и не отправляется автоматически по почте.

Клиент вводит код и входит через SkiF4er ID. Принимается только подтверждённая почта, совпадающая с приглашением. Код погашается атомарно вместе с привязкой `iss + sub`; повтор, просрочка и отзыв не проходят. Клиент получает отдельный read-only кабинет с названием одного проекта и одной согласованной редакцией PDF на 30 дней после принятия либо до отзыва владельцем. Следующий вход с тем же ID открывает действующий кабинет без повторного кода. Клиент не становится внутренним пользователем или членом организации. Нельзя открыть задачи, поиск, другие проекты, документы/версии, CSV, аудит или интеграции; URL скачивания не принимает ID выбранного пользователем файла. Новая версия документа не заменяет разрешённую. Владелец может отозвать приглашение/грант, что аннулирует и его OIDC-сессии. После истечения или отзыва для нового доступа выдаётся новый код. Одновременно допускается один активный кабинет на subject.

- `php tests/auth_security.php`: реальные RSA-подписи, ротация ключей, неверные claims, logout token, RFC-векторы PKCE/TOTP, шифрование, MFA-ограничения.
- `python3 tests/auth_schema.py`: схема SQLite 006, сохранение PDF и финансов, ограничения изоляции.
- `php tests/auth_db.php` и `python3 tests/auth_e2e.py`: прикладная проверка приглашений, отзыва, MFA, HTTP и миграции; `php tests/auth_db.php --postgres` — перенос с заполненными таблицами авторизации в отдельную **пустую** тестовую PostgreSQL.
- На реальном Keycloak: зарегистрировать confidential client, проверить обычный и гостевой вход, смену RSA-ключа, истечение и refresh, отзыв сессии, backchannel, RP logout, неверный state/nonce, недоступность ID и аварийный вход. Проверить два проекта, две редакции PDF и невозможность прямого доступа клиента к чужим данным. Не используйте production-ключи для тестов.
- При восстановлении копии БД с авторизацией сохраните исходный ключ MFA и не переносите старые PHP-сессии. Повторно проверьте, что восстановленная копия не возвращает уже отозванные привязки/гранты; до публикации выполните сверку с журналом оператора и IdP.

## Управление идентичностью и сессиями (1.1.1)

Миграция 035 для обеих СУБД сохраняет идентичности, пароли, политики организаций и существующие данные. Старые сессии сотрудников без нового реестра больше не принимаются; войдите заново. Гостевые сессии по-прежнему проверяются существующим OIDC-реестром и грантом. Не переносите файлы PHP-сессий при восстановлении.

1. В mixed войдите по локальному паролю, откройте «Безопасность», подключите или подтвердите TOTP, введите текущий пароль и выберите «Привязать SkiF4er ID». Отдельный запрос OIDC использует `prompt=login`, `max_age=0`, state, nonce и PKCE S256. Провайдер должен вернуть подписанный свежий `auth_time`. Callback проверяет исходный UID, версию и handle сессии, свежесть того же TOTP и действующую политику; повтор, чужой/гостевой subject и конфликт привязки отклоняются. Email не участвует в объединении. После успеха все прежние сессии отзываются, войдите заново любым разрешённым способом.
2. Отвязка требует того же TOTP и знания действующего локального пароля. При required на установке или в любой организации пользователя она запрещена, даже для оператора. Это намеренно консервативное ограничение, сохраняющее доступ владельца и сотрудника. Аварийный пароль не считается обычным резервным способом. После отвязки все сессии отзываются.
3. Список показывает сессии сотрудников по типу, времени начала, последней активности и текущей сессии. Сессии ограничены 30 минутами простоя и 12 часами абсолютного срока. Отзыв выбранной сессии требует TOTP и CSRF, проверяется на следующем запросе; запросы, уже выполняющиеся в момент отзыва, не прерываются. Отзыв OIDC-сессии Workspace не является глобальным logout всех приложений у IdP. Доступность IdP проверяется существующим механизмом introspection; список не гарантирует, что внешний провайдер ещё принимает токены.

### Восстановление оператором установки

Доступно только доверенному оператору ОС через CLI, не владельцу произвольной организации. При утрате ID сначала подтвердите личность по независимому каналу и получите проверенный `sub` из административной консоли realm. Не используйте email или имя вместо subject. Зарегистрируйте заявку восстановления; не записывайте секреты или персональные документы в её номер.

```sh
php bin/workspace auth:history owner@example.com
php bin/workspace auth:recover owner@example.com '<проверенный-sub>' TICKET-123
php bin/workspace auth:policy
```

Замена выполняется в одной транзакции, не оставляя обязательный ID отвязанным; занятый subject отклоняется. Политика не ослабляется, права не меняются, все прежние сессии Workspace отзываются. Проверить вход и TOTP с пользователем, зафиксировать результат в заявке. При потере TOTP применяется прежняя отдельная процедура `auth:mfa-reset`; не сбрасывайте второй фактор только по запросу из неизвестного канала. История `auth:history` показывает последние 200 событий с временем, типом инициатора, действием и номером заявки, без токенов, паролей и subject; события до 1.1.1 не реконструируются. Ограничьте доступ к CLI и журналам ОС.

Приёмка: `php tests/identity_db.php`, `python3 tests/identity_e2e.py`, `python3 tests/identity_schema.py`; дополнительно на реальном realm проверьте `auth_time`, повтор callback, новую привязку, отказ провайдера и выход.
