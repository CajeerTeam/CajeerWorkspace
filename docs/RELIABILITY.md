# Надёжность интеграций · 0.8.4

Раздел «Надёжность интеграций» доступен владельцу организации с актуальным MFA. Он показывает состояния действующих очередей GitHub, Logs, Bots, Dropbox Sign и новой очереди сверки Servers/aaPanel, а также постраничный журнал ошибок и восстановления. Названия, документы, сообщения, токены и необработанные ошибки провайдеров в журнал не копируются.

## Транзакции и очередь

GitHub webhook и локальные изменения ставят задания GitHub в существующую очередь в той же транзакции; аудит Workspace формирует `logs_outbox` внутри бизнес-транзакции. Подтверждённые сообщения Bots и пакеты подписи сохраняются в своих очередях. Новая очередь `integration_jobs` хранит запросы чтения инфраструктуры (хост, хеш его цели и проект, инициатор и версия сессии), дедуплицирует активные задания и подтверждает результат только после свежих снимков обоих источников. Кнопка сверки проекта транзакционно создаёт задания инфраструктуры, планирует чтения GitHub, Bots и Dropbox Sign. После commit не требуется удерживать HTTP-сессию.

Worker захватывает задание с токеном и арендой, освобождает транзакцию до сетевого I/O, фиксирует состояние и технический журнал в одной транзакции. Устаревший токен не может завершить задание. Для инфраструктуры сохраняются также штатные блокировки/поколения синхронизации. Повтор чтения безопасен; запись с неизвестным результатом не выполняется автоматически повторно.

## Скорость и бюджеты

Ограничитель применяется при захвате задания штатными worker GitHub, Logs, Bots, Dropbox Sign и новым worker инфраструктуры. Персистентный token bucket общий для всех проектов/процессов в одной БД, отдельно для каждого провайдера, по умолчанию 120 заданий/минуту с burst 120. Это лимит **заданий**, а не точное количество HTTP-запросов: один job может выполнять несколько запросов. GitHub дополнительно сохраняет штатный `Retry-After`/rate-limit для установки. Прямые синхронные операции адаптеров (например, ручная `infra:sync`, публикация CMS и Forum) не охвачены этим лимитом. Конфигурация — только доверенный CLI-оператор; смена лимита сбрасывает доступный burst до нуля.

```sh
php bin/workspace reliability:rate logs 30
php bin/workspace reliability:rate github 20
php bin/workspace reliability:rate bots 20
php bin/workspace reliability:rate sign 10
php bin/workspace reliability:rate infra 5
```

* GitHub: штатный бюджет 8 попыток, backoff и DLQ `dead`. Сверка после переподключения ставит чтения текущего поколения; ручное возобновление старого задания требует неизменной связи и поколения.
* Logs: 8 попыток в пределах 12 часов от создания, прежний ключ идемпотентности и неизменный payload; `retry_budget` или отказ preflight 409 — остановка, ручной повтор только в том же окне и с тем же credential. После истечения окна разрешено лишь чтение по точному `request_id`, trace ID, source/project ID, времени и совпадающим полям. Пустой результат не означает отсутствие доставки. Локальные метаданные журнала Logs удаляются вместе с соответствующей записью outbox.
* Bots: штатный бюджет удалённых попыток 8, безопасные ручные повторы только через существующую проверку до отправки. Сбой передачи или GET — `uncertain`; сверка выполняет GET по исходному ID. После неизвестного результата автоматически планируется только GET. Ошибка GET повторяется с backoff в пределах 8 последовательных ошибок; исчерпание требует ручной сверки. Никакого автоматического повтора PUT/POST для неопределённой операции. Смена цели остаётся запрещённой.
* Dropbox Sign: 8 последовательных ошибок обработки (включая просроченные аренды чтения и preflight), после чего автоматический worker исключает пакет из выдачи. Успешный poll сбрасывает счётчик. При неизвестном результате отправки — только штатный adopt после проверки удалённого ID. Разрешён ручной перезапуск безопасного чтения, а для исчерпанного `queued` — повтор preflight заведомо ещё не отправленного пакета.
* Servers/aaPanel: 8 попыток с экспоненциальной задержкой (до 1 часа), `dead` после исчерпания; новый запрос или отдельное возобновление требует действующего владельца и привязки хоста. Состояние частично успешного чтения остаётся доступным в инфраструктурном модуле, но job не считается завершённым.

## Запуск

Сохраняйте существующие cron worker, добавьте новый. Все worker должны использовать одну БД. Пример:

```cron
* * * * * cd /srv/workspace && /usr/bin/php bin/workspace reliability:work 10
* * * * * cd /srv/workspace && /usr/bin/php bin/workspace github:work 10
* * * * * cd /srv/workspace && /usr/bin/php bin/workspace logs:tick 10
* * * * * cd /srv/workspace && /usr/bin/php bin/workspace bots:tick 10
* * * * * cd /srv/workspace && /usr/bin/php bin/workspace sign:tick 10
```

Запускайте команды для настроенных провайдеров. Настройте внешнее наблюдение за ненулевыми кодами CLI и проверяйте журнал. `reliability:work` обрабатывает только новую очередь инфраструктуры; не заменяет существующие worker. `logs:prune` по-прежнему очищает просроченные записи. CLI требует доверенного системного оператора.

```sh
php bin/workspace reliability:reconcile PROJECT_ID OWNER_ID
php bin/workspace reliability:retry PROJECT_ID OWNER_ID github JOB_ID
php bin/workspace reliability:retry PROJECT_ID OWNER_ID infra JOB_ID
php bin/workspace reliability:verify PROJECT_ID OWNER_ID LOG_JOB_ID
```

После отключения восстановите credentials и штатные привязки. Запланируйте сверку, запустите worker, проверьте текущие состояния. Отдельно разберите DLQ и неопределённые записи; ошибки CMS, Forum, Lite и деплоя разбираются штатными сценариями их модулей (не повторяются общим worker). Сверка инфраструктуры выполняется для привязанных хостов целиком; источник остаётся владельцем истины. Журнал не подтверждает доставку без квитанции, а `not_found` не даёт разрешения на повтор записи. Прямые операции публикации не переводятся на общий транспорт.
