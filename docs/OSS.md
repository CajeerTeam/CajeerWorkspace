# Open-source workflow · 0.3.3

## Полномочия и публикация

Работает для проектов типа `oss`. Maintainer — текущий владелец организации или участник с правом проекта `manage`. Для изменения профиля, приглашений, triage, комментариев, связей и выпуска веб-интерфейс требует свежий MFA. Отзыв проектной роли проверяется повторно внутри транзакции.

Из карточки проекта откройте **Open-source: triage, публичные вехи и выпуски**. Создайте профиль с уникальным slug и GitHub `owner/repository`. Они неизменяемы в текущей версии. Название и описание задаются отдельно от внутренних полей; публикация отключена, пока явно не выбран статус «Опубликован». Ссылка на витрину: `/?p=oss.public&slug=my-project`. Проверьте, что репозиторий публичный и подготовленные тексты не содержат закрытых данных. Старый процесс публикации по вехам не запрашивает GitHub API; новый процесс релизных линий 1.4.2 описан ниже.

Выберите внутреннюю веху и введите отдельное публичное название и описание. Состояние и срок берутся из выбранной вехи в момент публикации; последующие внутренние изменения не публикуются автоматически. До выпуска веху можно обновить; после выпуска её публичная запись неизменяема. Выключение профиля блокирует витрину, экспорт и contributor-доступ; уже полученные копии не отзываются. Повторное включение возвращает опубликованные записи и неотозванные доступы с действующим сроком.

## Contributor / maintainer

1. Maintainer выдаёт приглашение с псевдонимом и сроком 1–168 часов. 256-битный код отображается один раз, хранится только SHA-256. Передайте код защищённым каналом. Не публикуйте его в URL или публичных issue. Код не является подтверждением личности GitHub/SkiF4er ID.
2. В отдельном браузере или после выхода из внутренней учётной записи contributor открывает `/?p=oss.join`, вводит код. Код погашается транзакционно. Доступ действует 30 дней, сессия истекает при 30 минутах бездействия. Новый код для прежней записи сохраняет её историю и отменяет прежний доступ; сессия привязана к поколению кода.
3. Contributor регистрирует issue/PR по HTTPS-ссылке строго на настроенный GitHub upstream, добавляет заголовок и описание. Дубли URL отклоняются; повтор той же формы не создаёт новый вклад. Он видит только свои обращения и их обсуждения. Сессия contributor не предоставляет внутренний аккаунт, организацию, задачи, документы, финансы или аудит.
4. Maintainer переводит вклад в `reviewing`, отвечает в обсуждении, создаёт/выбирает задачу через обычное планирование. В карточке задачи указывает ту же upstream-ссылку и сохраняет её. В triage связывает ID задачи с вкладом. Проект и upstream должны совпадать. Можно отклонить вклад с комментарием. После `accepted`/`rejected` решение окончательно, обсуждение остаётся доступным. Отправка/ответы ограничены по частоте.
5. После завершения связанной задачи maintainer принимает вклад (`accepted`) и вводит отдельно проверенную публичную release note. Текст обращения, внутренние названия задач и комментарии в публикацию не копируются. У принятого вклада связь и публичная заметка неизменяемы.
6. Закройте внутреннюю веху по существующим правилам планирования. В OSS-разделе выберите её публичную запись, укажите тег, название, release notes и явно отметьте принятые вклады этой вехи. Сервер повторно проверяет завершённость, связь, уникальность тега и отсутствие прежнего выпуска. Снимок release notes и выбранных вкладов сохраняется транзакционно. Не создаёт релиз или тег на GitHub — это этап 0.4.x.

Поддерживается один выпуск на публичную веху, до 100 выбранных вкладов на выпуск. Для крупных выпусков разбивайте план на несколько вех. Тексты — простой экранированный текст, не HTML/Markdown. Витрина и JSON (`/?p=oss.export&slug=my-project&n=1`) показывают по 50 вех/выпусков на страницу; `next_page` указывает продолжение. Экспорт не содержит внутренних ID, учётных записей, непубличных обращений, контактов, финансов или файлов. Публичный текст вводится вручную; ответственность за его содержание лежит на maintainer. В обсуждении показываются последние 200 сообщений.

## Проверка и эксплуатация

* `php tests/oss_db.php` — сквозная бизнес-логика SQLite, `--postgres` — дополнительно перенос populated SQLite в чистую PostgreSQL и проверки доступа. `python3 tests/oss_schema.py` — миграция и внешние ключи. `python3 tests/oss_e2e.py` — веб-маршруты и изоляция contributor.
* Сопоставьте публичный JSON и HTML с подготовленными текстами; убедитесь, что секретные названия задач, частные комментарии и другие проекты отсутствуют. Отзовите contributor и проверьте, что текущая сессия больше не работает; повторный код старую сессию не восстанавливает. Выключите профиль и проверьте HTTP 404 на витрине и JSON.
* Миграция 010 не изменяет существующие данные и не публикует существующие OSS-проекты. Новые таблицы включены в перенос SQLite → PostgreSQL. Секреты приглашений и публичные заметки не включаются в прикладной аудит: аудит фиксирует тип события и идентификатор объекта. Для backup/rollback см. UPGRADE.md.

## Сопровождение релизных линий · 1.4.2

В OSS-профиле откройте «Сопровождение релизных линий и backport». Требуются права проекта `manage` и `connections`, для изменений — свежий MFA. Настройте существующий GitHub App с Contents/Metadata/Pull requests read; связанный репозиторий должен совпадать с upstream.

1. Создайте линии (например, `main`, `release/1.x`). Название и ветка неизменяемы и предназначены для публичного отображения; линию можно закрывать и возобновлять. До 50 линий на проект.
2. В каждой линии отфильтруйте triage: не назначено, запланировано, отложено, отклонено, готово, выпущено. Один и тот же вклад можно назначить нескольким линиям, без копирования исходного обращения. Для отложенного/отклонённого решения нужна внутренняя причина. Для готовности нужен уже принятый вклад и номер PR именно для этой ветки.
3. Выполните backport в GitHub обычным процессом команды, слейте PR в целевую ветку и создайте опубликованный GitHub Release. Workspace не выполняет cherry-pick, merge или создание тегов. В форме выберите до 10 готовых исправлений, введите точный тег, SHA и явно публичные название и changelog.
4. Workspace проверяет публичность репозитория, опубликованный релиз, SHA тега (включая annotated tags), принадлежность тега ветке и merge-коммита каждого PR тегу. Состояние локальных объектов повторно проверяется до транзакции публикации. При отказе API или изменении источника публикации нет. Доказательство относится к моменту проверки, не гарантирует неизменность внешних Git-объектов после публикации. Настройте защиту тегов и веток.
5. Витрина и JSON-экспорт получают отдельный `line_releases` с публичным changelog, веткой, SHA и ссылками. Исторические выпуски по вехам не меняются. Вклады с назначенными линиями публикуются через новый процесс, а прежние опубликованные вклады могут получить новые backport. Один вклад публикуется не более одного раза в одной линии; разные линии имеют независимые PR и теги.
6. Автор получает уведомление в своём обсуждении при смене состояния линии и публикации; в кабинете видны последние 50 обновлений и ссылки на выпуски. Причины задержки и внутренние сведения не передаются. Это уведомления внутри Workspace, без электронной почты или записи комментариев в GitHub. Личность автора определяется существующим приглашением, а не проверенным GitHub-аккаунтом.

Приёмка: `php tests/oss_maintenance_unit.php`, `python3 -B tests/oss_maintenance_schema.py`, `php tests/oss_db.php` и `php tests/oss_db.php --postgres`; на реальном upstream проверить два backport одного вклада, два тега, отсутствие повторных уведомлений и отказ при неправильном SHA/ветке. Миграция 041 добавляет три таблицы, не меняет исторические публикации.
