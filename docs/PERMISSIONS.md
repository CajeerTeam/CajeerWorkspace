# Полномочия и согласование · 0.2.1

## Модель доступа

Организация — граница данных. Владелец организации сохраняет полный доступ, но не может утверждать собственную заявку при двойном контроле. Остальным нужно явное членство в проекте. На странице проекта владелец назначает отдельную роль; значение «Роль организации» восстанавливает наследование. Смена проектной роли действует в существующей сессии на следующий запрос. Владелец может изменить роль организации в разделе «Команда»; это отзывает сессии пользователя. Явные проектные роли сохраняются отдельно от организационной роли.

| Роль проекта | Полномочия сверх чтения проекта и задач |
| --- | --- |
| Наблюдатель | Нет |
| Менеджер | Создание и изменение задач, чтение интеграций |
| Исполнитель | Изменение своих задач, чтение интеграций |
| Бухгалтер | Чтение финансов, создание и утверждение заявок |
| Читатель финансов | Чтение кассы, CSV и заявок |
| Создатель платежей | Чтение финансов, создание и отмена собственных заявок |
| Согласующий платежей | Чтение финансов, утверждение чужих и отклонение заявок |
| Юрист | Чтение PDF, загрузка документов и редакций |
| Читатель договоров | Чтение реестра, истории и скачивание PDF |
| Читатель интеграций | Чтение привязанных интеграций и протокола |
| Оператор | Чтение интеграций, привязка уже доступных в организации экземпляров из разрешённых проектов, отвязка |
| Аудитор | Чтение метаданных событий проекта, без доступа к финансовым суммам и PDF |

Роли фиксированные, не произвольные комбинации. Глобальные полномочия `people` и создание проектов остаются организационными. Только владелец меняет явные проектные роли и политику платежей. Для совместимости менеджер организации с правом управления проектом может добавлять/удалять участников с наследуемой ролью; изменение и удаление явных проектных ролей зарезервировано владельцу. Членство команды не выдаёт права проекта. Оператор не получает глобальный каталог чужих экземпляров: новый экземпляр сначала предоставляет владелец. CLI администратора ОС остаётся доверенной административной границей, не доступной из веб-интерфейса. Внешних команд деплоя и реальных банковских переводов в выпуске нет.

## Платёжный процесс

1. Владелец включает «Двойной контроль» на странице проекта. Для старых и новых проектов по умолчанию сохраняется прежний режим прямого проведения для бухгалтера и владельца. Создатель без права утверждения **всегда** создаёт заявку, независимо от настройки.
2. Создатель вводит сумму, валюту, дату и назначение в разделе «Финансы». В двойном режиме запись находится в «Платежи» со статусом `pending`; баланс и CSV её не учитывают.
3. Другой участник с правом утверждения принимает решение в разделе «Платежи». Утверждение создаёт ровно одну кассовую запись и фиксирует идентификаторы создателя и согласующего. Автор не может утвердить собственную заявку, включая владельца. Отклонённая/отменённая заявка не проводит сумму.
4. Сторно проходит тот же процесс. Для оригинала допускается только одно ожидающее сторно; для уже сторнированного движения новое сторно запрещено.
5. Повтор того же запроса идемпотентен; повтор с изменённым содержимым или новое решение после закрытия заявки отклоняется. Параллельные решения сериализуются штатной блокировкой БД. Политика фиксируется на момент создания заявки: отключение двойного режима не позволяет провести уже ожидающую заявку без второго лица.
6. При исключении из проекта/организации или отзыве права создания ожидающие заявки отменяются в той же транзакции. При утверждении дополнительно проверяются текущая активность и право автора, в том числе если учётная запись отключена через CLI. Уже проведённые записи сохраняются. Отзыв доступа не прерывает уже переданные клиенту байты ранее начатой выгрузки.

## Аудит

Раздел «Аудит» доступен владельцу и аудитору конкретного проекта. Фильтрация по организации, проекту и курсору выполняется в SQL. События организации видны только владельцу. Записываются успешные изменения проектов, задач, договоров, подключений, членства, ролей, приглашений, команд, политики платежей, заявок и решений. Запись события и бизнес-изменение входят в одну транзакцию. В миграции 005 импортируются старые записи `action_log`, если проект однозначно определяется по исходному объекту. Суммы, содержимое PDF, секреты и коды приглашений не записываются. Это прикладной журнал изменений, не криптографически защищённый внешний журнал безопасности; не охватывает все чтения, неудачные запросы и операции ОС/CLI. Резервируйте базу с журналом.

## Обновление

SQLite: остановить приложение и cron, сохранить код 0.2.0 и конфигурацию, применить новый архив, выполнить `php bin/workspace doctor`, `php bin/workspace migrations`, `php bin/workspace upgrade`. Автоматическая проверенная копия SQLite создаётся до миграции. Ожидаемая схема 5. Миграция не меняет старые денежные записи или PDF, сохраняет прежнее наследование ролей. Повторное обновление не повторяет SQL.

PostgreSQL: остановить все процессы записи; создать и проверить предварительную копию `pg_dump` в отдельном защищённом каталоге по руководству [ORGANIZATIONS.md](ORGANIZATIONS.md), желательно восстановить её в отдельной БД для проверки. Затем `WORKSPACE_DB=pgsql php bin/workspace upgrade` (без аргумента пути). Миграция 4 → 5 выполняется в транзакции. Автоматический pg_dump не входит в команду, оператор отвечает за копию. Для переноса SQLite сначала обновите исходник до схемы 5, затем используйте `postgres:import` с пустой целевой БД: новые таблицы входят в контроль количества и SHA-256. При возврате восстановите прежний код и исходный снимок, согласуйте операции после момента копии.

## Проверки

`php tests/permissions_roles.php`, `python3 tests/permissions_schema.py`, `python3 tests/permissions_e2e.py`; последний использует реальное приложение, PDO SQLite и cURL. `python3 tests/permissions_e2e.py --postgres` дополнительно переносит данные в пустую PostgreSQL БД и проверяет доступ после импорта. CI выполняет SQLite PHP 8.3–8.5 и отдельные тестовые PostgreSQL 14/16.
