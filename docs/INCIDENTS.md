# Инциденты и дежурства — 0.8.2

Владелец проекта в организации включает политику, выбирает действующего владельца/менеджера/оператора проекта и срок реакции (1–10080 минут). Срок фиксируется при первом обнаружении Workspace, в UTC. Повтор сигнала и переназначение не продлевают SLA. Просрочка сохраняется после подтверждения. Управлять карточками могут владелец, менеджер и оператор в рамках проекта; чтение — пользователи с правом connections. Все веб-действия требуют MFA. Отзыв доступа блокирует работу; назначьте нового ответственного.

## Сбор сигналов

Сначала настройте привязки согласно INFRASTRUCTURE.md и LOGS.md. Сверка Servers и aaPanel выполняется существующим `infra:sync HOST_ID OWNER_ID` (или из интерфейса инфраструктуры). Затем запускайте `incidents:scan PROJECT_ID OWNER_ID` или кнопку в разделе «Инциденты». Для регулярного контроля настройте обе команды в cron с интервалом меньше 15 минут; при ошибке sync всё равно выполните scan. Не объединяйте команды через `&&`: сигнал ошибки API также важен. CLI требует действующего владельца организации. Повторный запуск безопасен; сканирование не выполняет перезапуски/деплой.

* Servers: свежая ошибка чтения Inventory и явный статус `offline`; `unknown`, `maintenance`, `provisioning`, `decommissioned` не доказывают отказ или восстановление. Inventory не является проверкой доступности приложения.
* aaPanel: ошибка чтения, отключённый/исчезнувший привязанный сайт, просроченный сертификат (дата UTC). Неизвестный сертификат не считается просроченным. Используются только актуальные законченные наблюдения (15 минут), не старые успешные снимки после ошибки. Отсутствие наблюдения не доказывает отказ. Каждый сигнал относится к привязанному сайту/окружению.
* Logs: только фильтрованные события Workspace `error`/`critical` из связанного источника, последние сутки, максимум 50 на уровень. При усечённой выборке CLI возвращает 1; уменьшите интервал сканирования и проверяйте Logs вручную. Не полный сбор произвольных логов и не потоковая система алертов. Ошибки Logs не блокируют сбор инфраструктуры. Дедупликация по Request ID; открытые сигналы группируются по источнику, условию, объекту, окружению и (для Logs) выпуску. При повторном отказе после восстановления создаётся новый инцидент. Прямые инфраструктурные сигналы и события Logs сохраняются отдельно.

## Работа и восстановление

1. Откройте карточку сигнала. Событие Logs с release_id сохраняет проверенную связь с выпуском. Для остальных оператор выбирает выпуск того же проекта; связь необратима, не означает доказанной причины отказа.
2. Назначенный ответственный подтверждает реакцию. При изменении назначения срок не сбрасывается. Изменения защищены версией карточки.
3. Выполните исправление штатными средствами источника, внесите причину, исправление и результат повторной проверки в отчёт.
4. Для Servers/aaPanel требуется новый успешный снимок того же условия, более поздний, чем последний зафиксированный отказ. Неизвестное состояние, смена привязки или просроченный снимок блокируют закрытие. Для Logs можно проверить более поздний разрешённый сигнал `host.*.ok`, `bots.sent` или `deploy.succeeded` того же объекта/окружения/выпуска. Для прочих случаев допускается явно подтверждённая независимая проверка оператором с описанием метода и результата; она помечается `manual`, а не автоматической проверкой. Отсутствие ошибок не считается подтверждением.

Сохраняются время обнаружения/первого и последнего сигналов/реакции/восстановления, нормализованные технические поля, источник, авторы действий и отчёт. Исходные сообщения, секреты, IP, ответы API не копируются. Отчёт вводится пользователем: не включайте секреты. Карточки и минимальные доказательства являются самостоятельным журналом инцидентов, не удаляются вместе с истечением срока хранения Logs. Ограничьте доступ к резервным копиям; отдельная политика очистки инцидентов не предусмотрена. История доступна в карточке (последние 100 записей каждого типа). Для полного аудита оператор может выгрузить данные из БД в защищённом режиме. Сканирование не отправляет уведомления и не управляет графиком смен: один активный ответственный на проект, SLA и список просрочек.

С 1.4.3 в сверку включены подтверждённые отказы управляемых развёртываний зарегистрированных сервисов. Связи поддержки, SLO и backlog описаны в [SERVICE_OPS.md](SERVICE_OPS.md). Для записи отказа из локального задания используется существующий класс событий deploy.*; в evidence указано `managed_deployment_record`. Это не результат запроса к Logs. Повторный сигнал Logs по тому же заданию не создаёт отдельную карточку.
