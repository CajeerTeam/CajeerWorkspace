# Рабочее место тимлида · 1.4.1

В проекте откройте «Рабочее место тимлида / Review» (`?p=lead&project=ID`). Доступ — существующие права `work` и `connections`. Владелец и менеджер с `manage` назначают и заменяют ревьюеров, отменяют review, регистрируют причины ожидания и технические решения. Все изменения — POST с CSRF, отдельным ключом идемпотентности и свежим MFA. Ревьюер — действующий сотрудник этого проекта с обоими правами; исполнитель задачи не может быть её ревьюером. Отзыв прав не удаляет историю.

## Review

Свяжите основной PR задачи в GitHub, запустите штатную синхронизацию и worker. Нужен свежий (до 15 минут) успешный снимок открытого PR. Менеджер назначает ревьюера с причиной. Замещение добавляет новое событие и сохраняет старое; прежний ревьюер больше не может принять решение. Назначенный ревьюер выбирает «Принять» или «Запросить изменения» с обоснованием. Проверяются точный SHA, репозиторий, его поколение, номер и версия связи. При новом SHA или устаревшем наблюдении требуется синхронизация и при необходимости новое назначение. Последнее решение относится к наблюдаемому SHA, а не к текущему удалённому состоянию GitHub между синхронизациями. Это внутреннее review, не GitHub approval и не блокировка merge; действующие QA и release gates не меняются. Дополнительные PR из карточки поставки остаются в Delivery, очередь тимлида работает с основным PR задачи. Фильтры «Все PR», «Ожидают review» и «Мои review» доступны сотруднику. Страница показывает до 50 связанных задач с переходом на следующую страницу и последние 20 событий для каждой.

## Технические решения

Создайте ADR с названием, контекстом, альтернативами и предлагаемым решением/последствиями, при необходимости укажите задачу. Открытое решение принимается или отклоняется менеджером с обоснованием. Исходная запись и финальное событие сохраняются; повторное или конкурирующее принятие отклоняется. Для нового решения создайте новый ADR. В отчёте открытые решения перед принятыми/отклонёнными, до 100 последних актуальных записей; полная история остаётся в БД.

## Зависимости и задержки

Используются реальные `task_dependencies`. При добавлении незавершённой зависимости или повторном открытии предварительной задачи записывается начало ожидания, при удалении связи или завершении предварительной задачи — окончание. Обе записи происходят в той же транзакции, что изменение задачи/зависимости. Причину указывает менеджер. Для зависимостей, существовавших до обновления, время начала неизвестно: при первой записи причины сохраняется нижняя граница времени наблюдения, а не выдуманная длительность. Закрытые до первого наблюдения старые интервалы не реконструируются. Длительности относятся к отдельным зависимостям и могут перекрываться. В отчёте до 100 активных зависимостей и 100 последних закрытых интервалов; вся история хранится в БД. Изменения причин регистрируются в аудите.

## Приёмка

Выполните `php tests/team_lead_unit.php`, `php tests/team_lead_db.php`, `python3 -B tests/team_lead_schema.py`; в PostgreSQL-матрице `php tests/team_lead_db.php --postgres`. На живом GitHub проверьте назначение, замену, новый SHA, отзыв проектных прав, блокировку устаревшей формы и повтор запроса. Для зависимости подтвердите начало, причину, завершение и повторное открытие; проверьте разные проекты и организационную изоляцию. Открытое и принятое ADR должны быть различимы. Миграция 040 добавляет три таблицы без изменения прежних данных. Для возврата к 1.4.0 требуется восстановление схемы 39.
