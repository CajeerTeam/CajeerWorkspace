# Dropbox Sign · подписание и архив (0.6.2)

## Область применения

Один утверждённый PDF (до 2 МиБ) и два разных подписанта по email, не встроенный процесс Dropbox Sign. Владелец проверяет полномочия подписантов и соответствие PDF тексту согласования, явно разрешает передачу файла и адресов провайдеру. Документ и решение 0.6.1 фиксируются по конкретной редакции, даже если впоследствии создана новая. Подписание не активирует договор и не заменяет бухгалтерский акт автоматически. Это интеграция e-sign, не квалифицированная электронная подпись (QES) и не налоговый ЭДО. Оператор и юрист проверяют допустимость метода, требования к идентификации и правила обработки персональных данных.

## Настройка

1. Создайте выделенный аккаунт Dropbox Sign с доступом к API для одной организации. Не используйте тот же аккаунт в другом Workspace. Проверьте лимиты тарифа, согласия, регион хранения и параметры доступа. В настройках оставьте стандартную выдачу PDF с audit trail, не включайте отделение audit trail. Не меняйте файлы, подписантов и метаданные запроса через Dashboard после отправки.
2. Настройте переменные окружения в PHP-FPM и CLI (секреты через защищённое хранилище, не в git):

```sh
WORKSPACE_SIGN_API_KEY=YOUR_API_KEY
WORKSPACE_SIGN_ORG_ID=1
WORKSPACE_SIGN_ACCOUNT_EMAIL=provider@example.com
WORKSPACE_SIGN_TEST_MODE=1
```

`WORKSPACE_SIGN_TEST_MODE` обязателен: 1 — тест, 0 — реальная отправка. Не переключайте режим, организацию или аккаунт при незавершённых пакетах. Ключ не сохраняется в БД. Ротация ключа требует проверки callback; архивные подписи проверяются старым ключом только в защищённом окружении. Указывайте email requester из API. Для отправки используются Basic Auth и фиксированный HTTPS origin; нет переадресаций.

3. В API Dashboard настройте account callback URL `https://workspace.example.com/?p=sign.webhook`. Веб-сервер должен сохранять заголовок `Content-Sha256`, разрешать POST multipart и лимит тела не менее 1.2 MB; PHP `post_max_size` должен быть больше этого. Ограничьте частоту запросов на reverse proxy, не журналируйте тела callback и заголовки авторизации. Успешная проверка callback подтверждается строкой `Hello API Event Received`. Проверяются HMAC всего JSON (base64 hex SHA-256) и event_hash (hex HMAC от event_time + event_type). Подлинные события других пакетов не обрабатываются. Не используйте отдельный произвольный webhook-secret вместо API key.
4. Установите cron от непривилегированного пользователя приложения с теми же переменными, БД и каталогом данных. Для PHP-FPM/CLI рекомендуется `memory_limit` не менее 256M, учитывая подписанный PDF до 16 МиБ и base64. Настройте HTTP timeout для ручной сверки (до 270 секунд); предпочтительно worker.

```cron
* * * * * cd /srv/workspace && /usr/bin/php bin/workspace sign:tick 10
```

## Работа

В «Согласование» редактор, юрист и владелец согласуют PDF. В «Подписание» владелец после MFA выбирает редакцию, вводит имена и email двух подписантов, подтверждает передачу. Пакет один на редакцию (в том числе тестовый или отменённый; для нового запроса подготовьте и согласуйте новую редакцию). Worker ещё раз проверяет актуальность редакции и действующие права всех участников, затем отправляет точные байты через `/v3/signature_request/send` с уникальными метаданными `workspace_nonce`, `workspace_evidence`. Dropbox Sign добавляет страницу подписей, если не задана разметка полей. Подписанты получают письма от провайдера. Не пересылайте приглашения другим лицам.

Состояния: queued, sending, uncertain, pending, partial, declined, provider_error, archived, cancelled. До отправки возможна отмена. После отправки статус проверяется через GET `/v3/signature_request/{id}`; для отмены удалённого запроса используйте Dashboard. Если удалённый запрос недоступен (например после отмены) Workspace сохраняет ошибку сверки и не считает его подписанным. Callback только сохраняет квитанцию и ускоряет сверку. Опрос раз в минуту для незавершённых запросов; ошибки откладывают повтор на пять минут. Worker использует аренду 300 секунд; запрет повторного POST после неизвестного результата предотвращает двойные письма/платные запросы. При uncertain проверьте Dashboard по nonce и восстановите существующий ID через форму «Сверить с провайдером»; GET должен подтвердить аккаунт, режим, nonce, хеш согласования и состав подписантов. Если провайдер не создал запрос, не пытайтесь повторить POST для этой редакции: согласуйте новую после проверки.

После is_complete и подтверждения всех подписей выполняется GET `/v3/signature_request/files/{id}?file_type=pdf`, затем повторный GET статуса. HTTP 409 при подготовке файла не считается завершением; worker повторит чтение. Полученные байты PDF, статус и SHA-256 сохраняются транзакционно. Workspace не проверяет криптографическую цепочку PDF и не утверждает юридическую действительность подписи; доверяет авторизованному API провайдера. Предполагается стандартная конфигурация, в которой audit trail включён в объединённый PDF; наличие отдельной audit trail страницы следует проверить при приёмке. Test mode не является юридически значимым подписанием.

## Архив

Видят участники с legal на проект и свежим MFA. Исходный и подписанный PDF скачиваются отдельно. Комплект `evidence.json` содержит base64 обоих PDF, SHA-256, версию шаблона и текст, решения согласования, список подписантов, ID запроса, сырой ответ отправки, финальное состояние, все сохранённые callback и API-квитанции. Callback HMAC фиксируется как получен, секрет не включается. У каждой квитанции свой SHA-256. Перед выдачей проверяются хеши, выдача журналируется. Документы не отправляются по открытым ссылкам. Данные хранятся в БД, входят в backup и перенос SQLite → PostgreSQL; ограничьте доступ к резервным копиям. Защиту от администратора БД, WORM, политики хранения и временные ссылки планирует 0.6.3. Не удаляйте архив при откате приложения: восстановление старой БД не отменяет удалённые подписи.

## Приёмка

Автоматические тесты: `php tests/signing_unit.php`, `python3 tests/signing_schema.py`, `php tests/signing_db.php`, `php tests/signing_db.php --postgres` (нужна пустая PG БД). Тесты используют внедрённый транспорт, не отправляют реальных писем.

Перед LIVE: test_mode=1, две контролируемые тестовые почты, проверить отправку и частичную подпись, отказ отдельного запроса, повторный callback, завершение и загрузку PDF с audit trail. Сравнить исходный SHA-256 и экспорт доказательств, восстановить backup, проверить доступ в другой организации и отозванные права. Проверить неудачную отправку и восстановление ID, отсутствие повторных писем. Убедиться, что архив помечен TEST. В новой согласованной редакции после приёмки можно использовать LIVE с отдельным подтверждением. Данная приёмка не выполняется автоматически в CI.
