# CajeerBots · поддержка и доставка Workspace 1.7.2

## Совместимость и установка

Проверяемая база: CajeerBots 1.0.2, commit `f1366da1c548b124af379b139f381dbc3ab165e6`. Штатный API 1.0.2 читает существующие outbound messages и поддерживает retry, но не создаёт произвольное исходящее сообщение. Поэтому в поставку включён **обязательный рабочий патч** `integrations/cajeerbots-1.0.2-workspace.patch`. Он добавляет ограниченный API и использует штатную таблицу/worker, меняет обработку retries только для ID с префиксом `workspace-`. Отдельной версии/миграции Prisma нет.

1. Остановите все процессы записи обеих систем и сделайте проверенные резервные копии обоих кодовых деревьев, БД, конфигураций и объектного хранилища Workspace. Проверьте отсутствие незавершённых запросов.
2. В отдельном дереве исходников CajeerBots выполните `git apply --check /path/to/workspace/integrations/cajeerbots-1.0.2-workspace.patch`, затем `git apply /path/to/workspace/integrations/cajeerbots-1.0.2-workspace.patch`. Если вместо patch используется отдельный архив изменений Bots, не применяйте patch повторно. **Не запускайте старые worker, scheduler, runtime или CLI с новым API.** Соберите `pnpm install --frozen-lockfile`, `pnpm build`, `pnpm typecheck`, `pnpm test`. Для Docker пересоберите образы и разверните одновременно все процессы. См. `docs/workspace-delivery.md` в Bots.
3. Обновите Workspace до 1.7.2 (`php bin/workspace doctor`, `migrations`, `upgrade`, `migrations`, `version`). Ожидается схема 51. Запускайте только новый код.
4. Настройте выделенный аккаунт бота, разрешённый тестовый канал и убедитесь, что бот имеет право писать туда. Используется Telegram (группа/supergroup/channel с ID `-100…`) или VK (positive peer ID); Discord, вложения, кнопки и рассылки по множеству каналов не поддерживаются.

## Конфигурация

Создайте в Bots API-ключ с ровно двумя scope: `workspace:messages` и `community:COMMUNITY_ID`, без `*`, `platform:global` и других разрешений. API-ключ должен иметь отдельный ID (не его значение). Установите в API и worker Bots одинаковый `WORKSPACE_BOT_TARGETS` (JSON):

```json
{"API_KEY_ID":{"communityId":"COMMUNITY_ID","accountId":"ACCOUNT_ID","provider":"telegram","channelId":"-100123456789"}}
```

Создайте приватный файл `/etc/workspace/bots-targets.json` вне docroot, доступный на чтение пользователю PHP-FPM/CLI:

```json
{
  "1:1": {
    "origin": "https://bots.example.com",
    "community_id": "COMMUNITY_ID",
    "account_id": "ACCOUNT_ID",
    "provider": "telegram",
    "channel_id": "-100123456789",
    "credential_id": "API_KEY_ID",
    "token_env": "WORKSPACE_BOTS_P1_TOKEN"
  }
}
```

Ключ карты — `organization_id:project_id`. Используйте фактические ID; `channel_id` обязательно строка. В окружении PHP-FPM и CLI задайте `WORKSPACE_BOTS_TARGETS=/etc/workspace/bots-targets.json` и `WORKSPACE_BOTS_P1_TOKEN` (значение ключа Bots, не токен Telegram/VK). Не передавайте секреты в командной строке или через веб. На стороне Bots токены провайдера остаются в штатной системе secret/env. Используйте HTTPS с валидным сертификатом и без перенаправлений. Файлы конфигурации и карты назначения доступны на запись только оператору.

Связь проекта с одной целью неизменяема: отдельный ключ, сообщество, аккаунт, канал. Дубли назначения `(origin,account,channel)` или ключа запрещены. Владелец включает привязку с проверкой удалённого API и MFA. Отключение предотвращает новые handoff, но не останавливает уже принятые удалённые задания; при необходимости отзовите ключ/allowlist на стороне Bots и выполните сверку. Замена API key ID или целевого канала требует отдельной операторской миграции, не подменяйте конфигурацию существующей привязки. При смене `updatedAt` аккаунта отмените неотправленный старый черновик/задание и создайте новый предпросмотр. Ротация значения токена по тому же tokenRef сама по себе не меняет `updatedAt`; не переносите ссылку на другой аккаунт во время доставки.

## Маршрут

Из карточки подтверждённого выпуска откройте «Сообщение Bots», подготовьте публичный текст (ссылка или краткое описание выпуска по необходимости), сохраните предпросмотр. Допускается самостоятельное текстовое сообщение без релиза. Для выпуска существует одно неотменённое сообщение. Предпросмотр неизменяем: текст, destination, удалённый ID, SHA-256 и снимок подтверждения, версия аккаунта, хеш доказательств релиза. Для исправления до отправки отмените и создайте новый черновик. Проектный менеджер/владелец подтверждает отдельной операцией MFA. Отправка не выполняется из GET или при создании предпросмотра. Перед передачей worker проверяет права подтвердившего, его session version, активность цели, целостность снимка и редакцию аккаунта. Читатели с `connections` могут просматривать историю и текст, но не отправлять.

```sh
php bin/workspace bots:tick 10
```

Пример cron: `* * * * * cd /srv/workspace && /usr/bin/php bin/workspace bots:tick 10`. Учитывайте время HTTP и лимит; параллельные вызовы координируются DB-lock/claim. При штатном состоянии remote pending/sending следующий GET возможен через 30 секунд. Отдельный штатный worker CajeerBots доставляет сообщение провайдеру. Без него очередь остаётся pending.

| Состояние | Действие |
|---|---|
| draft | Сохранён точный текст; подтвердить или отменить. |
| queued | Ожидает выполнения команды; create можно отменить локально. |
| processing | Аренда задания 60 с, не повторять. При истечении — uncertain. |
| pending | Принято Bots, но ещё не подтверждено провайдером; возможна отмена. |
| sending | Worker захватил задачу, отмена невозможна. |
| failed | Ошибка до handoff, безопасный повтор той же записи или отмена. |
| retryable | Bots подтвердил отказ до вызова провайдера; повтор той же записи, максимум 8 claims. |
| sent | Сохранена проверенная квитанция Bots с providerMessageId. Это не отметка о прочтении. |
| uncertain | Только точечная GET-сверка; не повторять запись автоматически. |
| cancelled | Отменено до отправки, сохранена история. |
| closed | Оператор закрыл неизвестный результат без подтверждения и без повтора; новая запись для того же релиза не создаётся. |

После потери ответа PUT/POST используется точный ID, а не поиск по тексту. Если Bots не подтверждает результат (в том числе 404 после потери ответа), оператор сверяет состояние и историю канала в Bots/провайдере. Не интерпретируйте 404 как гарантированную недоставку. При закрытии uncertain поздняя доставка всё ещё возможна; это не отмена. Ошибка после начала запроса Telegram/VK считается неопределённой, даже если могла быть явным отказом. Уведомление не отправляется автоматически при подтверждении релиза; требуется отдельное подтверждение человеком. Рабочие события `bots.sent/failed/uncertain/cancelled` могут экспортироваться в Logs с correlation ID выпуска, но без текста, канала, токенов или ответа провайдера.

## Приёмка и восстановление

В реальном тестовом канале проверьте: один выпуск → одно сообщение; повтор формы и CLI не отправляют второе; отмена локального queued и remote pending; отзыв полномочий до handoff; выключенный аккаунт до provider call; потеря HTTP-ответа и GET-сверка; запрет повторения неизвестной отправки. Для полного E2E нужен работающий Bots 1.0.2 с патчем, Redis, PostgreSQL, bot token и согласованный тестовый канал. Без этих проверок production-приёмка не завершена.

Откат обоих кодов и восстановление старой БД допустимы только после остановки всех процессов и сверки внешних эффектов. Старый worker способен повторять `sending`/`failed`, поэтому не возвращайте его на БД с незавершёнными Workspace ID. Сохраняйте исходную БД и журнал для расследования, не удаляйте remote rows вручную. Квитанции и история могут содержать чувствительное содержание сообщения, ограничьте доступ и резервные копии. Не публикуйте внутренние данные в общем канале.

## Поддержка и обратная связь (1.7.2)

- Матрица совместимости: исходный CajeerBots 1.0.2 commit `f1366da1c548b124af379b139f381dbc3ab165e6`, обязательный включённый патч, протокол `workspace-delivery-v1`. CI проверяет применимость патча и собирает закреплённый upstream. `/workspace-target` удостоверяет протокол и цель, но не версию сборки. Оператор подтверждает соответствие развёрнутого кода этому commit и patch; иной upstream требует новой стендовой приёмки. Не подменяйте версию лишь настройкой health.
- Владелец видит точное назначение из защищённого файла до включения. Хеш цели проверяется при сохранении; изменившийся канал отклоняется. Одна неизменяемая цель на проект, Telegram либо VK. Внутренние support-данные не копируются в текст.
- В `?p=bots&project=ID` или из `service_ops` выберите запрос вместо выпуска. Снимок ответа включает ID и версию обращения. Изменение обращения до handoff блокирует передачу; отмените безопасно неотправленный черновик и создайте новый. Идентичный текст для того же обращения не регистрируется повторно, пока предыдущий не отменён. Отдельное подтверждение точного текста и канала обязательно.
- Обратная связь: сотрудник с `manage` и `connections` после MFA вручную регистрирует ID сообщения (Telegram message_id либо VK ID сообщения в выбранном диалоге, используйте один устойчивый ID), время UTC, автора, тему, описание и сервис. Повтор того же ID с теми же данными возвращает исходный запрос; изменённые данные отклоняются. Запрос создаётся в `ops_support`, привязывается к каналу и обрабатывается существующим Service Operations. Это не webhook и не подтверждение получения от API. Не записывайте секреты и лишние персональные данные.
- Очередь ручной сверки: uncertain/failed/retryable, истекший processing, queued/pending/sending без изменения состояния за 15 минут. Успешный GET без смены состояния не сбрасывает возраст. GET ограничен существующим бюджетом сетевых отказов; оператор может повторно запросить GET. После потери ответа или при 404 нельзя повторять PUT/POST. Закрыть uncertain можно только с основанием, после сверки последнего события; результат остаётся `closed`, не `sent` или `cancelled`. Закрытие не исключает позднюю доставку. Проверяемая квитанция добавляется в историю при изменении состояния, числа попыток или ID; старые квитанции задним числом не создаются. История доступна постранично.
- `php tests/bots_support_unit.php`, `python3 -B tests/bots_support_schema.py`, `php tests/bots_db.php` и `php tests/bots_db.php --postgres` (изолированная БД). Реальная приёмка требует отдельно установленного патченного upstream, Redis, worker и тестового канала. Проверить ввод обратной связи, дедупликацию, изменение обращения после подтверждения, ошибку сети, ручную сверку и отсутствие повторной доставки. Миграция 051 не меняет прежние записи. Перед откатом сверить внешние эффекты и восстановить снимок схемы 50.
