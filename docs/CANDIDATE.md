# 0.9.2 — Release Candidate: заморозка и приёмка

Схема 33 заморожена: `database/schema-freeze.json` фиксирует SHA-256 всех 66 миграций SQLite/PostgreSQL из 0.9.1. Хеш файла заморозки закреплён в сборщике и PHP-коде. Сборщик проверяет обе серии, приложение — используемую серию и журнал БД. Не регенерируйте файл заморозки для обхода проверки. Нужное изменение схемы требует снятия статуса кандидата, отдельного согласованного выпуска и повторной приёмки. Это контроль целостности SQL и журнала, не доказательство отсутствия произвольного DDL на действующей БД.

## 1. Подписанный дистрибутив

Собирать полный ZIP, а не архив изменений. Ключ подписи RSA или ECDSA хранится у ответственного за релиз вне репозитория. Не хранить закрытый ключ на веб-сервере. Доверенные SHA-256 предыдущего ZIP и публичного ключа получить по независимому каналу; не вычислять их из непроверенного скачанного файла и не считать контрольную сумму подписью.

```sh
python3 tools/release.py build --output /secure/dist
python3 tools/release.py verify /secure/dist/CajeerWorkspace-0.9.2.zip
python3 tools/candidate.py sign /secure/dist/CajeerWorkspace-0.9.2.zip \
  --private-key /secure/release-private.pem --output /secure/dist/0.9.2.sig
python3 tools/candidate.py verify-signature /secure/dist/CajeerWorkspace-0.9.2.zip \
  --signature /secure/dist/0.9.2.sig --public-key /secure/release-public.pem \
  --key-sha256 "$TRUSTED_RELEASE_KEY_SHA256"
```

`openssl dgst -sha256` подписывает байты полного ZIP. Изменение одного байта делает проверку невозможной. Подпись тестовым ключом не является подписью владельца проекта. CI проверяет тестовый ключ; официальный ключ вводится только оператором. Пакетный CI зависит также от проверок Bots и recovery PostgreSQL.

## 2. Офлайн-обновление 0.9.1 → 0.9.2

Используется POSIX, Python 3.9+, OpenSSL CLI и PHP 8.3+ с нужными драйверами. На пилоте заранее создайте новый приватный каталог релизов; веб-сервер/worker должны читать код из `current/public` / `current/bin/workspace`. Команда prepare создаёт новый каталог, не накладывает файлы поверх старой установки. Код и приватный управляющий каталог принадлежат доверенному оператору; обеспечьте только необходимый доступ runtime на чтение/проход по каталогам (например, отдельная группа с доступом 0750 к каталогам кода и 0440 к файлам, без права записи), запрет записи для веб-пользователя. `WORKSPACE_DATA`, `WORKSPACE_OBJECT_DIR`, конфигурации подключений, ключи и сессии — вне каталога релизов; не используйте `config/connections.local.json` внутри неизменяемого дерева. Укажите `WORKSPACE_CONFIG=/secure/connections.local.json` во всех runtime. См. `docs/INTEGRATIONS.md`. Настройки необходимо перенести и проверить отдельно. Сохраните код исходного релиза и его настройки. Остановите HTTP, FPM, cron, CLI, worker и все иные процессы записи; флаг не останавливает процессы автоматически.

```sh
export WORKSPACE_RECOVERY_OFFLINE=1
# На 0.9.1, с его code root:
python3 tools/recovery.py backup --backend sqlite --data /srv/workspace-data \
  --objects /srv/workspace-objects --destination /secure/pre-092
# Сохраните manifest_sha256 из JSON в независимом хранилище.
# Для PG: WORKSPACE_DB=pgsql и явные PGHOST/PGPORT/PGDATABASE/PGUSER/PGSSLMODE,
# --backend pgsql без --data. Проверьте также restore в отдельную БД.

# Из доверенного кода 0.9.2:
python3 tools/candidate.py prepare --root /srv/workspace-release-set \
  --previous /secure/previous/CajeerWorkspace-0.9.1.zip \
  --previous-sha256 "$TRUSTED_PREVIOUS_ZIP_SHA256" \
  --candidate /secure/dist/CajeerWorkspace-0.9.2.zip \
  --signature /secure/dist/0.9.2.sig --public-key /secure/release-public.pem \
  --key-sha256 "$TRUSTED_RELEASE_KEY_SHA256"
python3 tools/candidate.py upgrade --root /srv/workspace-release-set \
  --backup /secure/pre-092 --backup-sha256 "$TRUSTED_BACKUP_SHA256" \
  --data /srv/workspace-data --objects /srv/workspace-objects
```

Проверяются точные хеши обоих пакетов и файлов, схемы и журнал миграций, соответствие текущих данных снимку, `doctor`, `version`, `migrations`, штатный `upgrade` (без миграций), повторный логический снимок. Состояние данных и объектов должно быть неизменным. Записывается привязка точки отката к каталогу данных/объектов и БД. `current` атомарно переключается только после проверки. Авария до переключения оставляет прежний код; после переключения проверяйте `readlink current` и повторно используйте те же параметры. Успех не запускает веб-сервис, не подтверждает внешние операции и не изменяет настройки FPM/Nginx. Команда создаёт приватное дерево 0700; если runtime работает отдельным UID, настройте группу и права только для root/release-директорий и кода, оставив управляющие файлы 0600; каталоги данных и объектов должны оставаться 0700 для их runtime. `config/connections.local.json` из старого дерева не переносится автоматически.

## 3. Откат

До включения записи выполните репетицию возврата:

```sh
python3 tools/candidate.py rollback --root /srv/workspace-release-set \
  --backup /secure/pre-092 --backup-sha256 "$TRUSTED_BACKUP_SHA256" \
  --data /srv/workspace-data --objects /srv/workspace-objects
```

Проверяется тот же снимок, тот же target и исполняемый 0.9.1. Откат меняет только `current`, не удаляет/перезаписывает БД или объекты. Если после выпуска были записи, инструмент откажется от возврата. Не заменяйте backup другим снимком для обхода. Остановите обе площадки и проведите контролируемое восстановление в отдельный каталог/БД по [RECOVERY.md](RECOVERY.md). Сопоставьте изменения после снимка и внешние побочные эффекты; не теряйте платежи, документы и отправленные сообщения. Согласуйте перенос или ручное восстановление операций до cutover. Храните прежние ключи, включая MFA, для прежней копии. При любом сомнении оставьте восстановленную площадку в карантине. Не допускайте одновременно пишущих старого и нового узлов.

## 4. Эксплуатационная приёмка

- Чистая установка: `doctor`, `init`, `migrations` (current=target=33, pending=[]), `health.php` (ready); проверить HTTPS, сессии, MFA, login/logout, гостя, отрицательные проверки доступа.
- Пилот: повторить четыре сценария из [PILOT.md](PILOT.md), девять подключений и контроль реального репозитория. Проверить проектную и межорганизационную изоляцию, платёжный dual control, экспорт и выдачу PDF; не выдавать доступ к Forum при недоступности ACL.
- Локализация: русский интерфейс UTF-8, формат даты DD.MM.YYYY, суммы в minor units и RU-запятая, UK VAT в GBP с десятичной точкой. CSV и HTML безопасны. Это не добавляет новые налоговые юрисдикции или языки интерфейса.
- Проверить логический снимок на копии реальных пилотных данных, перейти с 0.9.1 на 0.9.2, повторить read-only smoke, вернуть 0.9.1, проверить хеши, затем вновь переключить кандидат. Любая запись в этот период должна блокировать code-only rollback. На SQLite сравнить 136 таблиц, финансовые итоги, очереди, документы, объекты и связи; на PG применить native pg_dump/restore.
- После успешной проверки переключить HTTP на `current/public`, перезапустить PHP-FPM (включая OPcache), проверить health, входы и доступы. Включать worker по одному только после сверки внешних операций. Наблюдать ошибки и нагрузку; при инциденте остановить запись и выполнить соответствующий сценарий возврата. Не подменять откат удалением данных.
- Перед 1.0.0 сохранить отдельно: SHA-256 и подпись кандидата, протоколы CI/стенда, результаты четырёх сквозных сценариев, p95/RTO/RPO, дату и ответственного за допуск, список открытых дефектов. Любой критический дефект денег, документов, изоляции либо неподтверждённый rollback блокирует допуск. Автоматические тесты не являются актом production-приёмки.

## 5. Проверки

`php tests/candidate_unit.php` — независимая матрица ролей и локализация; `python3 tests/candidate.py` — подпись, неизменность схемы, отказ повреждённых пакетов, чистая SQLite-схема; с `WORKSPACE_PREVIOUS_RELEASE=/path/CajeerWorkspace-0.9.1.zip` дополнительно проверяется фактический предыдущий выпуск и переключение/откат на тестовых данных. `doctor` должен проходить для нативной проверки. При отсутствии расширений тест явно помечает нативный сценарий skipped; тест управления состоянием использует подмену только вызова CLI smoke. CI отдельно собирает предыдущий выпуск из истории Git, требует нативный runtime и запускает этот сценарий. При отсутствии исходного 0.9.1 в истории предоставить проверенный полный ZIP отдельно, не имитировать его заменой VERSION.
