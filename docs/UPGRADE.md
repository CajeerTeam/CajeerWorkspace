# Обновление и возврат · 0.1.2

## Требования и подготовка

64-разрядный PHP 8.3 или новее в пределах 8.x, PDO SQLite (SQLite 3.27+), cURL с HTTPS, sessions. Python 3.9+ нужен только для сборки/проверки дистрибутива и E2E, не для работы PHP. Выполните от пользователя установки `php bin/workspace doctor`: JSON показывает каждую проверку, код 0 — всё выполнено, 1 — недостающие требования. Веб-приложение проверяет те же требования в FPM; CLI и FPM могут использовать разные php.ini. Проверяйте `/health.php` после запуска FPM.

Поддерживаемые исходные схемы: 1 (0.1.0), 2 (0.1.1) и 3 (0.1.2). Переход к 3 не меняет бизнес-таблицы 0.1.1; добавляет журнал миграций. Для схемы 1 также выполняется штатная миграция 002. Номер `PRAGMA user_version` должен соответствовать фактической структуре. Базы неизвестных или более новых версий не обновляются. Не редактируйте SQL уже выпущенных миграций, не меняйте `user_version` вручную. Новые SQL-файлы должны содержать только операции, допустимые внутри транзакции SQLite, без собственных BEGIN/COMMIT/ROLLBACK, VACUUM и изменения user_version.

1. Остановите **все** процессы этой установки: HTTP/FPM, cron `sync`, административные CLI. Обеспечьте эксклюзивное окно обслуживания. Не запускайте старый код на обновлённой базе.
2. На старом коде сохраните отдельную копию кода, конфигурации, настроек окружения и секретов (защищённое хранилище). Сделайте дополнительный снимок базы: `php bin/workspace backup /srv/backups/workspace-before.sqlite`. Каталог уже должен существовать, находиться вне docroot, поддерживать жёсткие ссылки и иметь ограниченный доступ. Зафиксируйте SHA-256 этой копии (`sha256sum`), даже если старая команда его не выводит.
3. Проверьте новый полный дистрибутив по инструкции ниже. Разверните новый код в отдельном каталоге либо примените проверенный ZIP изменений поверх старого кода. Не затирайте локальную конфигурацию, данные и секреты. При отдельном каталоге явно установите одинаковый абсолютный `WORKSPACE_DATA` и `WORKSPACE_CONFIG` для CLI и FPM.
4. На новом коде проверьте `doctor` и `migrations`. Выполните обновление (пример для Linux):

```sh
export WORKSPACE_DATA=/srv/cajeer/data
export WORKSPACE_CONFIG=/srv/cajeer/config/connections.local.json
php bin/workspace doctor
php bin/workspace migrations
php bin/workspace upgrade /srv/backups/workspace-pre-012.sqlite
php bin/workspace migrations
php bin/workspace version
```

Команда `upgrade` без аргумента создаёт уникальную копию `pre-upgrade-vN-*.sqlite` внутри каталога данных. С аргументом использует новый абсолютный путь; существующий файл не перезаписывается. Копия создаётся **до изменений** под блокировкой записи SQLite: независимое соединение читает согласованный снимок (`VACUUM INTO`), выполняются quick_check и foreign_key_check. Снимок синхронизируется на диске и публикуется с правами 0600 (на Unix дополнительно синхронизируется каталог), выводятся путь, исходная схема и SHA-256. Сохраните этот вывод. Снимок включает все PDF и денежные операции; не включает JSON конфигурации и сессии. Планируйте свободное место для копии и транзакции; резервные копии на том же диске не защищают от его потери.

Все ожидающие миграции, журнал и `user_version` фиксируются одной транзакцией. Если копия не создана/не проверена, SQL не выполняется. При ошибке SQL изменения откатываются, предварительный снимок остаётся доступен. Повтор успешно завершённого `upgrade` не повторяет SQL и не создаёт лишний снимок. `init` не обновляет существующую старую схему, HTTP тоже. В журнале `origin=legacy` означает принятую после сверки структуры миграцию, а не исторически наблюдавшуюся дату установки; `recorded_at` — время записи в новый журнал. Новые миграции имеют `origin=applied`. Контрольные суммы сверяются и при открытии базы приложением.

5. Убедитесь, что `migrations` возвращает `current: 3`, `target: 3`, `pending: []`, три записи журнала. До открытия доступа запустите FPM, ограничив трафик проверяющим оператором. Проверьте `/health.php`, вход, количество проектов и задач, итоги по каждой валюте, скачивание обеих редакций контрольного PDF и совпадение SHA-256. Запустите `sync` для настроенных подключений и проверьте профиль. После приёмки верните пользовательский трафик и cron.

## Возврат к предыдущему выпуску

Миграции только вперёд. Не пытайтесь удалить таблицу журнала или вручную уменьшить номер схемы. Если ошибка произошла до фиксации миграций, старый снимок всё равно сохранён; проверьте состояние базы и выберите возврат на заведомо корректный снимок.

1. Остановите FPM/HTTP, cron и CLI. Сохраните обновлённую базу и логи отдельно для анализа. Любые операции после времени снимка отсутствуют в восстановленной базе: согласуйте их повторный ввод/сверку перед возобновлением работы.
2. Проверьте SHA-256 исходного снимка по значению из вывода команды либо по отдельно сохранённому хешу. Верните **точный старый выпуск**, его настройки и секреты. Не копируйте старый код поверх новых файлов без проверки состава; используйте отдельный каталог со старым дистрибутивом.
3. Создайте новый пустой каталог данных с правами 0700 и скопируйте проверенный снимок как `workspace.sqlite` с правами 0600. Не переносите старые `-wal`, `-shm`, `sessions/` и `sync.lock`. Пример (от пользователя установки, пути замените своими):

```sh
sha256sum /srv/backups/workspace-pre-012.sqlite
mkdir -m 700 /srv/cajeer/restored-011
cp /srv/backups/workspace-pre-012.sqlite /srv/cajeer/restored-011/workspace.sqlite
chmod 600 /srv/cajeer/restored-011/workspace.sqlite
export WORKSPACE_DATA=/srv/cajeer/restored-011
# Переключите тот же WORKSPACE_DATA, WORKSPACE_CONFIG и docroot в FPM.
cd /srv/cajeer/releases/0.1.1
php bin/workspace version
```

4. Проверьте `/health.php`, вход, проекты, деньги, документы, контрольный хеш PDF, затем включите cron и трафик. Не удаляйте исходный каталог до завершения проверки и согласования всех операций после снимка.

## Сборка полного релиза ZIP

Из чистой копии исходников:

```sh
python3 tools/release.py build --output dist
python3 tools/release.py verify dist/CajeerWorkspace-0.1.2.zip
cd dist && sha256sum -c CajeerWorkspace-0.1.2.zip.sha256
```

Сборка проверяет согласованность `VERSION`, константы версии, непрерывность SQL 001…N и явный список файлов. Содержимое архива располагается в корне, без обёрточной директории. Включены приложение, SQL, документация, тесты, CI, пример конфигурации и сборщик. Локальные данные, конфигурация, `.env`, VCS и зависимости не попадают в пакет. Новые штатные файлы необходимо добавлять в список `FILES` сборщика. Существующие артефакты не перезаписываются. С фиксированными исходниками и одинаковой реализацией ZIP/zlib сборка воспроизводима. Внутри ZIP `SHA256SUMS` для каждого файла, отдельно `<архив>.sha256` для всего архива. Проверка проверяет оба уровня, состав, версию, отсутствие повторяющихся и небезопасных путей. Выполняйте её **доверенной копией сборщика из репозитория**, до распаковки. SHA-256 обнаруживает повреждения, но не удостоверяет автора: получайте контрольную сумму из доверенного канала; подписанные пакеты не входят в этот выпуск. CI собирает и проверяет полный пакет после матрицы тестов; публикация/подписание релиза остаются ручными.
