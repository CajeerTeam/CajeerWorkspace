# 1.5.2 — Управление несколькими командами

Откройте «Ёмкость команд» (`?p=capacity`). Раздел доступен владельцу текущей организации после свежего MFA. Владелец управляет всеми командами организации; проектный менеджер сохраняет прежний доступ к своему проекту и не получает права на другие проекты. Никаких новых полномочий членам команды не выдаётся.

## Планирование

1. Выберите понедельник недели (UTC). Для каждого сотрудника заполните семь значений доступности в минутах (0–1440). Ноль означает отсутствие, включая отпуск и выходные; отсутствие сохранённого календаря означает неизвестную ёмкость. Причину можно сохранить без медицинских или иных чувствительных подробностей.
2. Назначьте сотруднику минуты на проект и команду. Сотрудник должен быть активен, входить в выбранную команду и иметь право `work` в проекте. Одна команда на пару сотрудник–проект–неделя; сотрудник может входить в несколько команд. Все назначения организации суммируются по сотруднику, включая существующие старые записи. Превышение календаря запрещено. При сокращении календаря сначала уменьшите назначения. В разделе прошедшие недели доступны только для чтения.
3. Для переноса, например 480 минут из проекта A в проект B, выберите исходное и целевое назначения одного сотрудника. Для замещения выберите другого сотрудника, в том числе в той же команде и проекте. Система проверяет остаток исходного назначения и доступность получателя, затем вычитает и добавляет минуты в одной транзакции. При конфликте всё откатывается. Причина и предыдущие/новые значения записываются в аудит. Для замещения на несколько недель повторите операцию в каждой неделе; исполнители задач и ревьюеры не меняются автоматически. Для освобождения назначения укажите 0 минут, в том числе после отзыва прав сотрудника.
4. Проверьте сумму по командам, остаток доступности и прогноз. Для старых записей без команды нет автоматического назначения команде. Если календарь ещё не настроен, права отозваны, сотрудник отключён или суммарные назначения превышают календарь, план требует сверки и не участвует в прогнозе. При удалении команды её атрибуция снимается, но прежняя проектная доступность остаётся. Назначения без команды с проверенным календарём учитываются в проекте, отдельно от команд.

`project_availability` остаётся источником недельной ёмкости для старого раздела «Спринты и время». Атрибутированные назначения редактирует владелец через «Ёмкость команд». Неатрибутированные назначения можно редактировать прежней формой в рамках действующих прав, но при наличии календаря общий лимит применяется в обоих интерфейсах. Старые недели без календаря остаются доступными согласно прежним правилам. Планирование ограничено текущей организацией: если сотрудник работает в нескольких организациях, оператор должен согласовать ёмкость вне Workspace. План не меняет согласованные табели, ставки, проводки, закрытые периоды и сроки отдельных задач.

## Прогноз очереди

Для каждого проекта отображаются открытые задачи, количество задач без положительной оценки, количество заблокированных задач и оценённый остаток. Используется оценка из последнего незакрытого спринта минус утверждённые минуты данной задачи за всё время, с нижней границей 0. Оценка считается полной, а не оставшейся трудоёмкостью. Для задач без оценки точный прогноз невозможен. На восьми выбранных неделях остаток последовательно уменьшается на подтверждённую ёмкость соответствующего проекта. Текущая и прошедшие недели не используются для покрытия (неизвестен остаток рабочего дня и уже отработанное время); будущие недели без календаря не предполагаются доступными. Заблокированные задачи включены в оценённую очередь, их количество показано отдельно. Это оценка покрытия трудоёмкости, не календарный прогноз исполнения отдельных задач, не critical path и не план по навыкам. Новые задачи, зависимости и неучтённые часы могут изменить прогноз.

## Безопасность и приёмка

Все команды проверяют владельца, MFA, CSRF (HTTP), отпечаток недельного плана и уникальный ключ действия. SQLite использует BEGIN IMMEDIATE, PostgreSQL — общий advisory transaction lock. Транзакция включает изменения и аудит. Повтор идентичного запроса не переносит часы второй раз. Устаревший снимок отклоняется. Миграция 045 добавляет `capacity_weeks` и `capacity_teams`, не переписывает существующие данные.

Проверки:

```sh
php tests/capacity_unit.php
python3 -B tests/capacity_schema.py
php tests/capacity_db.php
# На изолированном PostgreSQL-контуре согласно CI:
php tests/capacity_db.php --postgres
# На отдельной пустой PostgreSQL БД (не на той же, что использовалась для переноса):
php tests/capacity_db.php --native-postgres
```

Для production-допуска проверить на двух командах и двух проектах перенос 480 минут, замещение при отпуске, отказ при нехватке ёмкости, повтор операции, отзыв доступа и совпадение утверждённых табелей до/после. Проверить, что прогноз использует изменённую ёмкость, а данные второй организации недоступны. Приложить доказательства `team_capacity`, `capacity_substitution`, `queue_forecast` к регламенту PRODUCTION.md.

### Регрессия 1.8.4

Первое сохранение недели передаёт все 13 значений в UPSERT. Проверьте первичное сохранение семи дней с причиной и автором, повтор с прежним ключом и снимком (одна запись и один аудит), отказ при изменённом повторе или устаревшем снимке, перенос часов и сокращение календаря до фактически назначенного остатка. Сокращение ниже назначений отклоняется без изменений. Проверка переноса SQLite → PostgreSQL и нативный PostgreSQL-сценарий выполняются в отдельных заданиях CI.
