# CajeerLogs 1.1.0 · Workspace 0.8.0

Интеграция использует `/api/v1/ingest` (синхронная durable запись), `/api/v1/logs` и `/api/v1/projects/{project}/sources/{source}`. Проверено по исходникам и `docs/Log-Ingestion.md`, `docs/HMAC-signature.md`, `docs/Log-Search.md`, `docs/Retention-Storage-Lifecycle.md` CajeerLogs 1.1.0. Нет зависимости от общего проекта Logs и нет отправки исходных данных аудита. Технические события создаются только после включения политики; историческая миграция не экспортирует данные.

## Настройка

На стороне Logs создайте отдельный проект и выделенный источник типа приложения для каждого проекта Workspace. Установите срок хранения источника (например 30 дней), включите штатный scheduler retention. Создайте **два source-bound токена**: reader `logs:read` и sender `logs:read` + `logs:write` (чтение нужно только для проверки собственной цели перед отправкой). Токены не должны иметь другие источники/проекты. По возможности включите обязательную HMAC подпись. Для v1 используется полный bearer как ключ; для v2 задайте отдельно key UUID и secret.

Оператор создаёт приватный файл вне docroot, доступный FPM и CLI только на чтение, например `/etc/workspace/logs-targets.json` (0600/0640 по модели пользователя запуска):

```json
{
  "1:1": {
    "origin": "https://logs.example.com",
    "project_uuid": "11111111-1111-4111-8111-111111111111",
    "source_uuid": "22222222-2222-4222-8222-222222222222",
    "source_slug": "workspace",
    "read_env": "WORKSPACE_LOGS_P1_READ",
    "write_env": "WORKSPACE_LOGS_P1_WRITE"
  }
}
```

Ключ карты `organization_id:project_id`, UUID замените фактическими значениями. Только HTTPS origin без пути, стандартный API prefix `/api/v1`; без redirect. Для v2 дополните `signing_key_id` и `signing_env` (имя переменной с отдельным секретом). Передайте `WORKSPACE_LOGS_TARGETS=/etc/workspace/logs-targets.json` и секреты через защищённое окружение FPM/CLI. Не публикуйте их в репозитории и не передавайте в URL. Нельзя использовать одинаковый удалённый проект для двух Workspace-проектов одной установки. Между установками соблюдайте то же правило операционно. В Workspace владелец открывает Logs → проект → подтверждает политику (MFA). Чтение доступно только проектной роли `connections` и свежему MFA. Не выдавайте эти роли сотрудникам без соответствующего разрешения на операционные журналы. Logs отдельно проверяет выданные токены; внешний Explorer использует собственную пользовательскую сессию и ACL.

## События, корреляция

Транзакционная очередь фиксирует только статические имена из `LOG_EVENTS`, числовые object ID, host ID, release ID, окружение dev/staging/prod, timestamp UTC, случайный request ID и 32-hex trace ID. Уровень определяется именем события. `release.*`, `deploy.*` и `editorial.*` получают один trace ID на выпуск; хостовые наблюдения aaPanel/Servers — один trace ID на окружение (не утверждают причину отказа или принадлежность к последнему выпуску). Сбой при проверке CI в составе приёмки выпуска отражается `release.failed` и `release.ci_failed` (неуспешная проверка CI, включая невозможность чтения), без произвольного сообщения об ошибке. Сбой GitHub sync отражается отдельным `github.sync.failed`. `task.create/state` имеют независимый trace ID. Не пересылаются actor IDs, названия проектов, тексты, комментарии, пути файлов, договоры, финансовые записи, сырые исключения, JSON API, URL запросов и credentials. Нет автоматической трассировки внешних приложений. Correlation ID привязан к локальной неизменяемой привязке проекта; `request_id` уникален для события.

В разделе Logs фильтры окружения, выпуска, correlation ID и уровня передаются в штатный поиск. Ответ проверяется на проект, источник, service, статический словарь событий, корреляцию, диапазон и выбранные фильтры; произвольные `message/context/tags` и все секреты отбрасываются. До 50 последних событий; уточняйте фильтр или используйте штатный Explorer `/admin/#logs` с самостоятельным входом и выбором проекта/источника. Сама SPA Logs 1.1.0 не принимает фильтры через URL. Из инфраструктуры и карточки релиза переход сразу открывает фильтрованный список Workspace. Есть ссылка на точный запрос к Logs API с теми же фильтрами (только собственная сессия/ACL Logs, никаких service credentials в URL), а также JSON-выгрузка не более 50 разрешённых записей из Workspace. Не используйте этот список как универсальный просмотр любых произвольных логов.

## Доставка и эксплуатация

```sh
php bin/workspace logs:tick 10
php bin/workspace logs:prune
```

Запускайте tick раз в минуту, prune не реже раза в сутки (tick также очищает очередь). Несколько worker координируются транзакционным claim с арендой 60 с, HTTP timeout 8 с. Отправка выполняется вне транзакции. Неизменяемые тело и ключ `workspace-<event_key>` повторяются, HMAC nonce и timestamp новые. Retry с exponential backoff, до 12 часов от создания (минимальное окно idempotency Logs 24 часа); после этого expired, без повторной отправки. Изменение bearer после попытки приводит к отказу доставки, чтобы не повторить запрос в иной цепочке ротации. При неизменённом bearer допустима ротация отдельного HMAC ключа. Ошибки хранятся только как фиксированные коды. `delivered` означает подтверждённый ingest, не гарантирует, что событие не было уже удалено политикой. Неопределённый результат после истечения окна требует ручной сверки в Logs; повторного POST нет. Отключение привязки не отзывает уже начатый HTTP-запрос; для немедленной остановки дополнительно остановите worker и отзовите токен в Logs. Не удаляйте локальные rows вручную, не переиспользуйте проект/источник и не запускайте старые копии БД параллельно.

Локальный TTL 1–365 дней, от создания события; уменьшение политики сокращает старые TTL, увеличение не продлевает их. Удалённый срок проверяется при включении, чтении и отправке: у источника должен быть конечный срок не больше локального. Logs применяет более короткую политику проекта/источника по received_at. Workspace не вызывает destructive remote API, не меняет внешнюю политику и не удаляет исходный audit; внешний оператор должен обеспечить scheduler и контроль `retention:history`/`retention:preview`. Перед сокращением срока в Logs используйте штатный процесс с backup и preview. Отключение привязки не удаляет удалённые записи. Срок хранения резервных копий определяется отдельно. Контролируйте очередь и свободное место; не храните токены в логах самого PHP-FPM/Nginx.

## Проверки

`php tests/logs_db.php`, `python3 tests/logs_schema.py`, `php tests/logs_wire.php /path/to/CajeerLogs` (реальные классы валидации и HMAC из коммита `ec686ab677149de5472e207c3aa6a1f6f9392a75`); `php tests/logs_db.php --postgres` на отдельной пустой PostgreSQL БД. Проверки используют внедряемый транспорт, не заменяющий production cURL. Перед production включением проверьте настоящий Logs 1.1.0: source-bound credentials, приём HMAC, повтор одного Idempotency-Key, выборку, отзыв токена, удаление по retention и независимую ACL Explorer. Для теста используйте отдельный проект.
